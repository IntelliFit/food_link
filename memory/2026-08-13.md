## 小程序识别记录页返回闪烁修复
- 用户反馈列表下滑后进入一条识别记录，返回列表时会先闪到顶部再回到原位置。
- 根因是 `useDidShow` 每次刷新都复用了首次加载的 6 条/20 条分阶段渲染；返回时列表高度在 80ms 后缩短、480ms 后恢复，触发 `ScrollView` 滚动位置夹取与恢复。
- 已在 `apps/wechat/src/packageExtra/pages/analyze-history/index.tsx` 通过 `hadLoadedOnce` 区分首次加载和后续刷新；后续刷新直接提交完整 `pageTasks`，首次进入仍保留性能优化。
- 用户录屏复验发现第二层分页问题：进入详情前已向下加载多页，返回时固定请求 20 条并覆盖整个列表，使当前项目变成列表底部；因为宿主已处于触底位置，不会自动再次触发 `onScrollToLower`，需先上滑再下滑才补回数据。
- 已进一步让 `useDidShow` 按当前已渲染的记录数刷新同等范围（上限与 API 一致为 200），并使用响应中的新游标继续分页；搜索等新查询仍按 20 条第一页重置。
- TypeScript 与目标文件 ESLint 均通过。`mrc` 不在 PATH，项目内无本地封装，3001/9420 未监听；未擅自启动本地常驻进程，本轮运行时滑动/返回复验和截图仍待开发者工具自动化可用后完成。

## 生产识别记录页全员超时事故

- 用户反馈首页正常、进入识别记录持续加载，线上用户普遍复现；授权只读调用生产 `/api/analyze/tasks?limit=20&offset=0` 并允许修复、部署、提交和推送。
- 最终根因有两层：
  1. 3 个 Pod 各 16 个 worker 每 2 秒同步执行保质期通知空轮询和 stale recovery，约 48 GORM ops/s、占数据库操作 98.24%，耗尽每 Pod 10 个连接的连接池；慢 trace 的绝大部分时间实际在等待连接。
  2. Apollo 的生产 `database.host` 使用同机公网 IP，Pod 到 PostgreSQL 经过公网 hairpin；连接池惊群修复后，完整 JSONB 列表仍有 2.5-20.2 秒抖动。改为现有 K8s Service 后，数据库阶段恢复到毫秒级。
- PostgreSQL 本身无锁等待、CPU/IO/缓存异常；同样 SQL 在数据库本机为毫秒级。Nginx JSON gzip 未启用会造成 146,719B 明文响应，但不是秒级超时主因。
