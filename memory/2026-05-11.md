- 用户询问当前系统中“食物能量分析”的后端流程如何实现。
- 已静态梳理当前 Go 后端链路：
  - 前端分析页先上传图片到 `/api/upload-analyze-image-file`，失败时回退 `/api/upload-analyze-image`。
  - 图片分析提交 `/api/analyze/submit`，文字分析提交 `/api/analyze-text/submit`，后端返回 `task_id`，前端 loading 页轮询 `/api/analyze/tasks/:task_id`。
  - `TaskService` 根据执行模式创建 `analysis_tasks`：
    - 标准模式：`food` / `food_text`
    - 精准模式：`precision_plan`，并创建或续接 `precision_sessions`
  - worker 用 `FOR UPDATE SKIP LOCKED` 领取 pending 任务，标准模式调用 `AnalyzeService.Analyze/AnalyzeText`，完成后写回 `analysis_tasks.result`。
  - 图片默认模型链路为 OfoxAI Gemini；文字默认 DeepSeek。
  - 标准模式默认 `db_first`：模型主要输出食物名称和重量；后端通过 `food_nutrition_library` 与 `food_nutrition_aliases` 查每 100g 营养，再按估重缩放热量和三大营养素。
  - 未命中食物会写 `food_unresolved_logs`；若 DeepSeek fallback 可用，会估每 100g 营养并写回 `food_nutrition_library(source=deepseek_auto)`。
  - 精准模式链路为 `precision_plan` → `precision_item_estimate` → DB-first 营养回算 → `precision_aggregate`。
  - 用户保存结果时，前端调用 `/api/food-record/save`，后端写 `user_food_records`，包括 `items`、`total_calories`、P/C/F 汇总与 `source_task_id`。

- 已按 `jinhui-stack-debug` 从数据依赖先查库：
  - 「饭饭」当前 `weapp_user.weight = 47.4kg`。
  - `user_weight_records` 最近记录：
    - `2026-05-09 07:35:40 +08:00`：`47.5kg`
    - `2026-05-09 07:35:52 +08:00`：`47.5kg`
    - `2026-05-09 07:36:00 +08:00`：`47.4kg`
  - 因此最后一次/最新一次体重是 `47.4kg`；同一天前两次和前一天 `2026-05-08` 是 `47.5kg`。
- 根因：
  - Go 后端 `/api/body-metrics/summary` 的 `aggregateWeightDaily()` 同日聚合旧逻辑用 `seen` 跳过后续记录，导致当天取第一条 `47.5kg`。
  - 用户档案同步和体重趋势链路取当天最后一条，因此显示 `47.4kg`。
- 已修复：
  - `backend/internal/health/service/body_metrics_service.go`：`aggregateWeightDaily()` 改为同日后续记录覆盖前一条，即每日 summary 取当天最后一次记录。
  - `backend/internal/health/service/body_metrics_service_test.go`：新增同日多条体重记录测试，锁定最新值 `47.4kg`、较上次 `-0.1kg`。
