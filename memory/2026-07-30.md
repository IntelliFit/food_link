## 视频食物分析方向

- 用户提出以 3–6 秒环绕短视频替代或补充拍照，估算食物身份、体积、重量和营养，并为未来 AI 饮食硬件接入距离、红外/深度传感器做准备。
- 已只读获取飞书知识库「api文档」：万界方舟 Gemini 原生接口文档列出视频分析能力，输入示例为 `fileData` 中的 `video/mp4` 与 `fileUri`。当前项目的 Gemini 原生实现只会下载图片并发送 `inlineData`，任务模型也只有 `image_url/image_paths`，尚未接入视频。
- 核心判断：视频大概率提升遮挡场景的食物识别与身份置信度，但不会自动带来可靠克重。直接视频 VLM 更适合语义；高精度份量需要关键帧筛选、跨帧实例跟踪/分割、相机位姿、深度/多视角重建和绝对尺度标定，之后通过食物密度换算重量。
- 推荐先以称重真值做离线 A/B，不直接改产品：单图、3 关键帧、原生视频 VLM、关键帧 + 多视角几何、RGB-D 五组，比较身份、重量、热量、拒识、时延和成本。未来硬件应同步 RGB、ToF/LiDAR 深度、IMU、相机标定与置信度；红外距离与近红外光谱应区分。
- 用户粘贴的疑似万界 API 密钥没有被调用、记录或写入项目；应尽快轮换后再用受控非敏感样本做接口验证。

- 用户说明当前身边没有食物秤，也不知道包装净含量；确认第一版希望采用最简单的多图方案，最终仍由 VLM 联合分析，后续再增加深度学习体积估计。

- 用户无秤不阻塞产品原型；真值评估先使用 Nutrition5k 等公开数据，后续由团队统一建立中式餐食称重集。没有真值时只能交付估算能力，不能判断或宣传绝对精度。
- 第二阶段深度学习候选：Depth Anything V2 提供单目深度先验，DUSt3R 提供多视角点图和相对位姿，结合跨帧实例分割、尺度锚点和网格积分计算体积。RGB 单独预测通常仍缺绝对尺度，需参考物、AR 公制位姿或 ToF/LiDAR。

## 聚餐扫桌的动态覆盖纠正

- 用户指出固定选择 3 张关键帧忽略了镜头移动和食物不同时入镜的问题，尤其不适用于聚餐、聚会、长桌或自助餐扫描。该纠正成立。
- 方案改为先按相机运动和画面重叠切分视野段，建立“候选帧—可见实例/桌面区域”覆盖矩阵，以最大覆盖动态选择关键帧；3 张只作为单次 VLM 调用批大小，整段视频可以产生多组调用。
- 多组结果需通过连续帧 tracklet、外观 embedding、容器形状和相机空间位置全局去重；无法确认是否重复时显式保留 `possible_duplicate_group`。
- 聚餐扫桌识别的是整桌食物，不代表用户实际吃下的食物。个人摄入需要后续选择份量、前后对比或硬件持续跟踪夹取/入口事件。
- 视频时长也改为动态：单盘约 3–6 秒，聚餐扫桌约 8–20 秒或直到覆盖完成；相邻视野保留约 30%–50% 重叠，避免镜头跳转后失去跨段判重依据。

## 样例视频的近景—全景结构澄清

- 用户说明样例是刻意先贴近逐项拍摄、滑动扫描，直到最后一秒才把所有食物同时拍入画面；前面的不完整入镜不是拍摄失误。
- 算法需识别帧职责：`detail_frame` 提供身份/OCR/局部形态，`overview_frame` 建立全局食物清单和去重锚点，`bridge_frame` 将近景 tracklet 挂接到全景实例，模糊的 `transition_frame` 通常不送 VLM。
- 推荐采集协议调整为可选起始概览、逐项近景、结束概览。最后全景用于确认前面近景是同一批食物，但不能只使用最后一帧，否则会丢失近景中更清晰的包装、品种和尺度信息。

## 通用关键帧发现前提纠正

- 用户明确指出样例的“近景滑动、最后全景”可能与真实拍摄完全不同，不应着急将其设计成固定协议；真实任务的挑战正是从任意视频中自主发现合适关键帧。
- 设计前提改为不假设帧顺序、不假设存在全景、不假设固定视频时长或固定关键帧数。帧职责由主体尺度、覆盖、文字清晰度、相机运动、画面重叠和时空关系自动推断。
- 关键帧选择采用粗到细迭代：低成本稠密扫描建立候选图，首轮形成食物清单，再按身份/OCR/数量/尺度/遮挡不确定性回看原视频补帧，直到边际收益不足或达到成本预算。
- 语义、OCR、去重和几何可能需要不同帧集合；不能把一组“最佳三帧”同时当作所有下游任务的输入。
