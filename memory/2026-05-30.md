## 包装零食库结构判断

- 用户强调：Gemini 重识别结果必须和 `packaged_food_library` 的结构对齐；库结构会决定后续图片分析、手动搜索和赚积分补库是否真正发挥作用。
- 当前库本质是 SKU 级单表：`brand/product_name/flavor_text/spec_text/barcode/net_weight_g/serving_weight_g/每100g营养/source_image_urls/ocr_raw_text/raw_label_payload/field_confidence/product_key`。
- 当前三条使用链路：
  - 图片分析试验模式：逐 item 判断是否包装食品，按 `barcode -> product_key -> alias -> canonical -> SearchPackagedFood` 解析，命中后用 `net_weight_g` 作为重量锚点，歧义多规格且无强证据时保留 AI 估重。
  - 手动搜索/上传前搜索：`/api/manual-food/search` 查 `packaged_food_library` 的品名、品牌、口味、规格、条码、分类，返回 `source=packaged_food`，默认重量优先 `serving_weight_g`，其次小包装 `net_weight_g`。
  - 主动上传赚积分：结构化后按条码/product_key upsert，新建才奖励，已有则更新不重复奖励。
- 设计风险：`spec_text` 仍是自由文本，缺 `unit_count/unit_weight/total_net_weight/net_content_unit/package_form/product_family_key` 等结构化规格；`packaged_food_aliases.normalized_alias` 全局唯一不适合多规格同名 SKU；分析链路和手动搜索链路目前使用不同检索实现，后续应收敛为同一个包装商品 resolver/search service。
