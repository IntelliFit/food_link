## 运动分析：修复 exercise_items NOT NULL 冲突

### 问题
运动分析保存时上报：
```
ERROR: null value in column "exercise_items" of relation "user_exercise_logs" violates not-null constraint (SQLSTATE 23502)
```

### 根因
- `user_exercise_logs.exercise_items` 字段为 `jsonb NOT NULL DEFAULT '[]'::jsonb`。
- 短文本/图片等链路估算完成后，`exerciseItemsFromEstimate` 返回 `nil`（只有长文本 library MET 模式才生成 items）。
- `ExerciseRepo.CreateExerciseLog` 未对 nil 切片做归一化，GORM 序列化时插入 NULL，触发约束冲突。

### 修复
- `backend/internal/health/repo/exercise_repo.go`：在 `CreateExerciseLog` 中，若 `log.ExerciseItems == nil`，将其设为空数组 `[]map[string]any{}`，确保写入 `'[]'::jsonb`。
- `backend/internal/health/repo/exercise_repo_test.go`：新增 `TestExerciseRepo_CreateExerciseLog_NormalizesNilItems` 覆盖 nil 场景；并改用 `modernc.org/sqlite` 纯 Go 驱动，避免 CGO 限制。
- `backend/internal/health/service/exercise_service.go`：增强 `exerciseItemsFromEstimate`：
  - 长文本 library MET：保留现有 items。
  - 分段估算：把每个 segment 解析成独立 item，提取时长/组数/次数。
  - 单条 LLM（短文本/图片）：用 `exercise_type` 生成一个 item，并从描述中提取时长/组数/次数。
  - `EstimateCalories` 响应也返回 `exercise_items`。
- `backend/internal/health/service/exercise_service_test.go`：在短文本、分段、长文本、图片等测试中断言 `exercise_items` 非空且字段正确。

- `backend/internal/health/repo/exercise_repo_test.go` 改用纯 Go SQLite 驱动（`modernc.org/sqlite`），解决本地 `CGO_ENABLED=0` 无法运行的问题。

## 调查：收藏食谱分享的早餐动态出现两张图片

### 现象
用户 `8826bc8d-81ad-40a4-bc42-6cc30506b8c3` 通过收藏食谱记录早餐后分享到圈子，发现动态展示两张图片，但收藏/识别记录只有一张自己拍的图。

### 定位
- 最新早餐记录：`user_food_records.id = 0243f554-1fce-429d-9056-0c3052b915e5`
- `entry_type = favorite_recipe`，`recipe_id = feddb9e7-db6a-4270-b6e1-89d2836de2fc`
- 食谱本身图片：`https://cdn-food-images.coachlink.fit/2d834649-45c5-4a1d-861f-4a6cb7daa78e.jpg`（用户自己拍的图）
- 记录 `image_paths` 为空，仅 `image_path` 有值。

### 原因
`backend/internal/community/service/community_service.go` 的 `normalizeFeedRecord` 在处理食物记录时调用 `foodmedia.EnrichFoodRecordDisplayFields`，该函数会：
1. 先加入记录自身的 `image_path`；
2. 再遍历 `items`，对每个 `manual_source = nutrition_library` 的条目回查 `food_nutrition_library` 的图片；
3. 把所有找到的图片合并写入 `record.ImagePaths`。

该早餐食谱包含两个条目，其中 `manual_source_id = 0a0b6ec6-da0f-460b-858a-d996b1b40461`（水煮蛋）在 `food_nutrition_library` 中有系统回填图 `standard-food/backfill/0a0b6ec6-da0f-460b-858a-d996b1b40461/cd9e6b14c42dbaf5.jpg`。于是圈子动态最终渲染出：用户自己拍的图 + 系统回填的水煮蛋图。

### 结论
第二张图片来自食物营养库的系统默认回填图，不是用户拍摄或收藏的图。当前逻辑在用户已有自己照片的情况下仍会追加营养库图片，导致出现「非本人图片」。

### 修复
- `backend/internal/community/service/community_service.go` 的 `normalizeFeedRecord`：
  - 在调用 `EnrichFoodRecordDisplayFields` 前保存记录自身图片；
  - enrichment 后，若记录原本已有图片，则 `record.ImagePaths` 只保留原始图片，不再混入营养库回填图；
  - 若记录原本无图，仍允许回退到营养库图片。
- 新增单测：
  - `TestNormalizeFeedRecordKeepsOnlyOriginalImages`
  - `TestNormalizeFeedRecordFallsBackToLibraryImages`
- 顺带修复社区模块若干测试签名不匹配（`ListComments`、`ListTargetComments`、`ListNotifications`），使 community service/handler/repo 测试可编译。
