- 测试问题 4：食物保质期本地和线上版本不同步。
  - 用户现象：刚在线上版本操作的保质期数据，在本地 Go 重构测试版里看不到。
  - 定位结论：这是优先级最高的数据依赖/环境依赖问题。线上 Python 旧链路通过 Supabase client 读写 `food_expiry_items`；当前 Go 后端通过 GORM 直连 PostgreSQL 读写同名表。若线上仍是 Python/Supabase、本地是 Go/PostgreSQL，两边不会自动同步。
  - 前端补充：保质期列表页 `src/packageExtra/pages/expiry/index.tsx` 进入时会直接请求 `getFoodExpiryDashboard()` 和 `listManagedFoodExpiryItems()`，不是先读本地保质期列表缓存；因此“本地看不到线上刚写的数据”主要不是缓存问题。
  - 后续建议：本地测试 Go 行为时在本地 Go 后端重新造数据；若要看线上 Supabase 的最新数据，需要先执行 Supabase -> PostgreSQL 同步/迁移，或让本地/线上临时连同一套后端与数据库。
  - 迁移脚本补充：`backend/scripts/migrate_supabase_db_to_postgres.py` 是全量 destructive 脚本，默认 drop/recreate 目标 schema 后恢复 Supabase dump 并校验；适合迁移/切流前同步，不适合 Go/PostgreSQL 已承接真实写入后定期覆盖。若要长期并行，需要设计增量同步或双写；当前脚本更适合手动 dry-run/最终同步。
  - Schema drift 补充：迁移/切流前必须先在临时目标库演练并跑校验。若 Supabase 与 Go 目标 schema 不一致，先决定 schema 真源；切流前通常以 Supabase 生产 schema 为源，Go 结构体、repo、migration 必须对齐。Go 侧新表/新字段要整理成正式 SQL migration，再纳入最终迁移计划。不要在正式目标库上边恢复失败边手工修。
  - 切流窗口补充：“旧数据丢失”更准确说是“暂时不可见”。如果 T0 做最终同步，T1 用户仍在旧 Python/Supabase 写入，T2 切到 Go/PostgreSQL，那么 T1-T2 之间的数据不会在 T0 快照中，新版本读新库时就看不到。安全做法是短暂停写：停旧写入 -> 最终同步 -> 校验 -> 切流 -> 开新写入；不要在新库已开始写入后再用 destructive 全量同步覆盖。
  - 双版本并行补充：体验版/本地 Go 写 PostgreSQL，正式线上旧版写 Supabase 时，两边都会产生数据。当前全量同步脚本不能直接覆盖已承接 Go 写入的 PostgreSQL。无丢失策略是：普通用户切流前只认 Supabase 为真源，Go 侧体验数据视为测试数据或单独备份；若体验版产生必须保留的数据，则最终切流要做双源合并/增量 upsert，而不是单向 destructive 覆盖。
