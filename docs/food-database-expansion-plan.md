# 食物数据库扩充方案（万界方舟辅助）

## 1. 当前结论

食物库不能简单追求“几十万行”。应先区分三类对象：

1. **标准食物/通用菜品**：如熟米饭、番茄炒蛋、熟米粉。核心是可靠的每 100g 营养、熟干态和别名召回，合理规模通常是数万条，而不是无限复制同义词。
2. **包装商品 SKU**：如品牌、口味、规格、条码不同的饮料或零食。市场规模可达几十万乃至更多，必须以包装标签、条码和真实照片为证据，不能靠大模型猜营养。
3. **餐馆/食堂菜品**：同名菜因门店、配方和份量而变化。应保存门店、菜品、实拍图和估算区间，不能伪装成统一营养真值。

万界方舟适合承担候选生成、名称规范化、图片理解、OCR 复核和缺图兜底生成；不适合作为营养真值的唯一来源。

## 2. 当前项目已有能力

- `food_nutrition_library` 已有 `quality_tier`、`quality_evidence`、图片来源和许可证字段，可表达数据可信度与溯源。
- `food_unresolved_logs` 已按未命中名称累计 `hit_count`，可以直接作为“按真实用户需求补库”的优先队列。
- `nutrition-backfill` 已能补已有食物的微量营养，也能对 unresolved 名称生成候选营养。
- `standard-food-image-backfill` 已能搜索 Bing/Google 图片、调用视觉模型判断食物是否匹配及是否有水印、转存 COS，并支持万界方舟 Gemini 原生多模态协议。
- 2026-07-31 只读统计：可参与图片回填的标准食物 9,626 条，已有图片 8,886 条，缺图 740 条，当前覆盖率约 92.3%。缺图中中文名 93 条、非中文名 647 条。

现有图片脚本写库时只更新 `image_path` / `image_paths`，尚未同步写入 `image_source_url`、`image_source_label` 和 `image_license`。因此它可以用于内部试跑，但在版权与来源字段补齐前不建议直接大规模上线搜索图片。

## 3. 推荐扩库流水线

### 3.1 候选发现

每天汇总以下信号，形成统一候选队列：

- `food_unresolved_logs.hit_count`：识别或搜索真实未命中；
- 用户保存前修改的食物名、重量、营养；
- 包装食品上传的 OCR、条码、品牌和规格；
- 公共食物库、校园/食堂、门店菜品上传；
- 权威开放数据集的新条目及版本更新。

优先级建议：`真实未命中次数 × 最近性 × 用户数 × 业务价值`。先补用户真的搜不到的 1,000 条，比让模型凭空枚举 10 万条更能提高命中率。

### 3.2 名称规范化与去重

使用万界文本模型把候选结构化为：

- `canonical_name`、简繁体/中英文别名；
- 食物类别、品牌、口味、规格、条码；
- `food_state`（raw/cooked/hydrated/fried 等）；
- `weight_basis`（dry/as_served/drained 等）；
- 是否是标准食物、包装 SKU 或门店菜品；
- 与现有 Top-K 候选的关系：同一条目、别名、上下位类或全新条目。

模型只提出候选关系。合并或新建前仍需经过确定性归一化、别名冲突检测、embedding/词法召回和严格身份门禁。

### 3.3 营养数据分级

按证据强度写入现有 `quality_tier`：

1. `authoritative`：国家/地区权威食物成分表、可复核开放数据库、包装营养标签；
2. `legacy_curated`：历史人工整理且通过一致性检查；
3. `reviewed_estimate`：模型估算后通过双模型、规则和人工抽检，仅允许精确名称命中；
4. `plausible` / `unreviewed`：候选区，不进入模糊召回和自动营养复用；
5. `rejected`：错误、重复或无法确定口径。

所有模型生成营养至少执行：非负/范围检查、4/4/9 热量闭合、熟干态门禁、同类分布异常检测、重复名称冲突检查。包装商品没有标签证据时，不生成“精确营养”。

### 3.4 图片策略

优先顺序：

1. 用户/商家授权的真实照片；
2. 明确可再利用许可的开放图片，并记录来源 URL、来源名和许可证；
3. 搜索图片只作为候选，由万界多模态模型检查主体、做法、熟制状态、水印和包装品牌，再进入人工/抽样复核；
4. 找不到合法图片时，用 `gpt-image-2-pool` 等生成“示意图”，必须标记 `image_origin=ai_generated`，不能当作商品或门店实拍证据。

随机抓取搜索结果并转存到自有 COS 不等于获得使用许可。无许可证信息的搜索图不应直接公开展示。

### 3.5 双通道发布

- **候选库**：允许批量、自动、低成本生成，但不参与线上模糊召回。
- **生产库**：只有证据完整、规则通过、达到质量阈值的条目才能提升为 active/可召回。

每条数据保留 `source`、模型与版本、prompt 版本、输入证据、生成时间、审核结果和可回滚批次号。

## 4. 万界方舟的具体分工

| 任务 | 推荐能力 | 结果用途 |
| --- | --- | --- |
| 名称扩展、别名、分类 | 文本模型 `/v1/chat/completions` | 生成候选，不直接上线 |
| 搜索图是否匹配食物 | Gemini/Qwen 多模态理解 | 图片审核与置信度 |
| 包装正反面 OCR 复核 | 多模态理解 | 标签字段候选 |
| 缺图生成 | `gpt-image-2-pool` / `gpt-image-2` | 仅作 AI 示意图 |
| 营养估算 | 文本模型 + 规则校验 | 只进入低可信候选层 |

手册已实测 `POST /v1/images/generations`，图片结果可能是 `b64_json`，需解码、校验后转存 COS；Gemini 原生多模态可通过 `generateContent` 输入图片。API Key 只从配置/环境变量读取，不写入任务结果或日志。

## 5. 第一阶段 P0（建议先做 1,000 条）

1. 只读导出 unresolved Top 1,000，并按标准食物/包装 SKU/餐馆菜品分类。
2. 使用万界文本模型生成规范名、别名、熟干态和去重判断，全部先落审计文件/候选表。
3. 权威来源优先补营养；模型估算仅作为 `unreviewed`，不直接 active。
4. 修复图片回填的来源、许可证和 AI 生成标记；先处理当前 93 条中文缺图，高价值优先。
5. 建立 200 条人工金标集，比较补库前后的 Top-1/Top-5 召回、错误复用率和熟干态错误率。
6. 达标后按批次 1,000～5,000 条扩展，而不是一次性生成几十万条。

## 6. 验收指标

- 用户真实查询 Top-5 覆盖率；
- 精确身份 Top-1 命中率；
- 错误营养复用率（最重要，宁可 fallback 也不能串食物）；
- 熟/生、干/湿、可食部口径错误率；
- 包装 SKU 条码/品牌/规格唯一性；
- 图片主体匹配率、许可证完整率、AI 示意图标记完整率；
- 每条通过审核的数据成本、P95 处理时延、人工复核率；
- 新增条目 7/30 天真实命中率，用于淘汰模型凭空生成但无人使用的数据。

## 7. 不建议的做法

- 让模型一次列出几十万种食物并直接写生产库；
- 将模型估算营养伪装为权威数据；
- 把别名、规格和烹饪状态全部展开成重复 canonical 行；
- 随机抓取搜索图片后不记录版权来源；
- 为真实品牌商品生成一张“看起来像”的包装图；
- 只看数据库行数，不测真实用户查询覆盖率和错误复用率。
