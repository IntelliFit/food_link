# 食探采集协议与算法程序改造方案

2026年10月16日 | 产品与研发讨论稿 | 配套采集规范 v1.0

## 核心决定

采集规范与算法必须共同设计。目标是让符合约定的素材在验证过的范围内自动完成结构化和入库，离场后的人工只处理少量例外，而不是把所有抄录与配图搬进另一张后台表单。评价指标是从采集到可用数据的总人工时间，尤其是后期整理时间，不是上传张数或模型识别出了多少菜名。

不能把当前算法尚未实测的能力写成采集承诺。本轮只形成文档，没有调用线上模型评测、迁移数据库或改动应用代码。以下能力分层与验收数字是建议目标，不是已实现或已测结果。

## 自动处理范围必须分层

| 输入类型 | 首期目标 | 自动处理边界 |
| --- | --- | --- |
| 同窗清晰文字菜单 | 自动拆条目、提名称及明确价格、保留单位与原文 | 位置明确、行列关系明确；无依据字段为空 |
| 名称紧邻配图的菜单 | 提条目与图文区域关联 | 图片标记商家示意；只绑定版式关系明确的图 |
| 套餐或多档价格 | 提套餐规则、选项和未明规格 | 不枚举组合，不给备选菜摊派总价 |
| 自选原料与计价牌 | 提窗口售卖规则及明确配料 | 原料不当成品；未知计价量不能标准化 |
| 标签同框的多菜实物 | 建候选区域，利用标签关联 | 标签归属明确，允许采集者现场一键纠正 |
| 无标签多菜照片 | 保存窗口素材 | 首期不自动精确配菜，不默认创建人工逐盘识别工单 |
| 模糊、缺页、混窗 | 指出具体问题、引导现场补采 | 无法补则降级保存，不伪造结构化结果 |

“保存资料”“符合采集要求”“无需人工处理”“可公开的字段完整”是不同状态。例如菜单没写单位可以拍摄合格，但系统只能发布原价描述，不能展示为确定的每份价格。

## 不能退回旧方案

不能要求一图一道菜、每道菜必有实物图；不能让工作人员逐条重打识别结果；不能让每批资料都等平台人员逐条审核。用户提供的事实默认可信，模型抽取和推测另设证据门槛。正常清晰素材最终应由系统直接处理或由采集者一次批量确认，平台以抽样和纠错治理质量。

## 采集动作与算法约束一一对应

| 采集端增加的动作 | 系统少承担的困难 | 程序必须配套的能力 |
| --- | --- | --- |
| 开始本窗口并确认位置 | 跨窗口聚类与归属猜测 | 会话内固定位置；换窗明确开新组 |
| 一张一个连续菜单区域 | 全景中搜索微小菜单、错配行列 | 检测菜单区域与文本密度，局部切片识别 |
| 分段重叠一两行 | 断行、漏菜与跨页重复 | 重叠项候选去重；冲突保留来源 |
| 记录页面是否拍全 | 把缺页误当停售 | 覆盖状态与条目状态分开 |
| 带上单位和套餐说明 | 凭常识猜规格与价格 | 价格原文、计价量、组合规则独立字段 |
| 标签同框或现场点名 | 离场后逐盘猜身份 | 区域关联、标签解析、照片级短注释 |
| 离场前只处理缺项提示 | 二次返场或后台追问 | 上传后快速预检，具体到照片及问题 |

菜单分辨率、文字占比、单图菜盘数量等阈值不能只凭经验写死。v1.0建议近拍相邻二至四盘，是降低难度的试行约束；应以真实设备测试决定是否放宽。不能仅用文件大小、总像素或模型自报置信度判断合格。

## 现场少量确认不能演变为变相录入

系统默认继承任务位置，自动保存上传进度。采集者只需确认分组、补现场独有信息、处理少数明确疑点。不要逐条弹窗确认每个菜名，不要求提前裁图。普通用户零散素材可以轻量提交；承担整窗任务的人才需要完整覆盖检查。

网络差时先保存本地待传清单和持久草稿，展示未完成状态；原图未传完不能显示整组成功。预检超时应允许离场并保留稍后反馈，不无限等待。失去现场确认机会后，无法解决的关联保留未知，不静默转成人工清洗队列。

## 不确定项分原因处理

SOURCE_ABSENT 表示现场未标明，允许字段留空；IMAGE_UNREADABLE 表示拍摄不可读，提示补拍；RELATION_AMBIGUOUS 表示关系不明，提示一次具体说明；MODEL_FAILURE 表示系统失败，应重试或降级，不归责采集员。不同原因影响不同字段，不一律阻止整批数据使用。

## 当前代码有哪些基础

以2026年10月16日本机 dev 分支工作区为观察对象。检查时 HEAD 为 fca734ad，另有多对话未提交修改，包括采集页面向社区等场景扩展；以下是工作区观察，不代表正式版功能或已完成验收。实施时须重新核对差异，保留其他任务修改。

| 位置 | 已有能力 | 需要调整或补充 |
| --- | --- | --- |
| 小程序 campus-food-collector 页面 | 多图上传、地点与代理权限 | 图片仍逐张变菜品；改为素材组与缺项处理 |
| campuscatalog domain 与 service | 批次、menu_item、combo、ingredient、价格选项 | 保留这些类型；补原图区域和字段来源关系 |
| community service 与 repo | 用户贡献、版本、纠错、冲突及回滚 | 复用版本机制，覆盖提取结果确认与来源变更 |
| Admin 食堂采集页面 | 批次查询、条目编辑与发布 | 补原图对照与少量例外处置，不新建全量人工录入流程 |
| 单条菜品分析链路 | 面向一条菜的异步营养分析 | 不当菜单解析器用；另设菜单提取任务 |

当前小程序选择图片使用 compressed，每张图建立一个含 name 的 DraftEntry；提交映射 entry_type 为 dish，有价格时写元／份，captured_at 取提交时刻。这些默认值都不适合历史混合素材。后端已有灵活类型，但不能据此声称菜单批量识别已经接通。

## 接口复用与新增边界

复用现有图片上传 /api/campus-food-collection/images 的鉴权与对象存储约束，但需支持菜单高清输入和可恢复上传状态。复用目录选择、采集员范围、已有修改历史与发布投影。现有 /api/campus-food-collection/batches 接收已整理 entries 并触发既有业务，不能悄悄把它改成“收素材立即公开”。

建议新增独立 capture-sessions 工作流接口，负责草稿、素材、分组、预检、提取状态、疑点解决和提交确认。最终确认结果再调用已有领域服务建立或更新条目。新接口存在的理由是生命周期不同，不是另做一套菜品库。

采集素材权限与批量发布权限分开。学生可以交素材，不自动获得跨窗口批量改写资格；付费任务认领不等于管理员权限。保留现有登录、内容安全、对象归属校验及违规处置，模型调用不可成为素材保存的同步阻塞。

## 建议数据结构

原始素材、模型观察和正式条目分层。原图不随提取结果改写，一张图可支撑多个条目，一个条目可引用多张图和多个区域。无需给每条菜单复制一份完整原图。

| 实体或关系 | 最少保存的信息 |
| --- | --- |
| 采集会话 capture_session | 地点范围、任务引用、实际拍摄时间及其来源、餐段、覆盖范围、规范版本、提交人、状态 |
| 素材 asset | 对象键、文件哈希、原文件名、尺寸、用途、会话归属；保留重复提交来源，不重复存相同内容 |
| 提取观察 observation | 原文、结构化字段、证据图及坐标、未知原因、提取版本、确认人或自动规则依据 |
| 图片关联 association | 图片区域到条目或窗口的关系、实物或示意图类别、依据、状态、创建与撤销记录 |
| 处理任务 processing_run | 输入哈希、模型与规则版本、运行状态、重试、费用、耗时、失败原因、目标会话版本 |

以上为逻辑结构建议，最终表拆分应遵循现有 Go 分层和事务边界。已整理结果继续进入 campus_food_catalog_items，修改继续记录 campus_food_revisions，公共显示沿用既有投影。独立任务认领系统与结算系统暂不列为第一阶段数据库开发项。

## 必须保持的业务含义

价格存数值时同时保留原文。金额、币种、计价数量、计价单位、规格与套餐规则分别表达。只有“0.8元”不能转换为“0.8元／份”或“0.8元／100克”。未知不能用0替代。两荤一素的6元属于组合，不属于每道备选菜。

拍摄时间、上传时间、最后确认时间分开。EXIF和文件名只作时间提示，不是不可修改的事实；采集者可确认或标记未知。新上传的旧照片不能覆盖更新的价格。重复菜单、宣传页、不同餐段和不同窗口同名菜，合并策略分别处理。

## 状态和并发

会话状态建议为草稿、上传中、预检中、提取中、可确认、部分待补、已提交、失败可重试。素材提交完成与条目公开完成分别反馈。用户离页后能恢复，服务端使用稳定请求键防重；重复回调不重复建菜。

提取结果必须绑定输入和目标版本，旧模型任务返回时不能覆盖新补充。提交正式记录前做版本检查与事务保护，部分失败有可追踪结果。更新与纠错保留前后版本；图片关联可以撤销重做，原始证据不覆盖删除。

## 算法流水线与人工边界

第一步检查上传完整性、文件重复、用途与窗口归属。第二步定位菜单与文本区域，必要时分片识别，避免整张全景缩成小图造成文字损失。第三步结合版面提取名称、价格、单位和选项，输出约束明确的结构化数据。第四步校验原文证据、名称与价格行关系、计价含义、重复项与冲突。第五步只将可解释结果提交确认或自动入库，未解决字段留空。

OCR负责读文字，多模态模型辅助版式、关系和类型判断；规则校验防止无依据字段进入正式库。具体模型或供应商本轮不指定，先用现有可用能力做最小试验，再按准确率、费用与延迟选择，不以换更大模型代替采集约束。

## 自动通过不能只靠置信度

清晰文字、有可定位的原文、明确行列关系、无冲突且通过已验证规则，才有资格进入自动通过范围。两个模型说法一致不等于事实正确；模型自报高置信度不等于实测可靠。自动通过规则必须在独立窗口样本上测过，按菜单类型分别报告质量。

初期采集者可整批浏览确认，系统突出少量异常；达到放行标准后，对验证过的类型开放免逐条确认，保留抽检和随时纠错。平台不应把所有记录排进人工审核队列。事实冲突时展示来源和时间，请有关贡献者补充；不能用最新上传时间简单覆盖。

## 不让异常变成新的人工黑洞

同一素材识别最多进行有限次数的定向重试，仍无结果则保留未知或退回一个具体问题。按会话和错误原因聚合提醒，不给用户逐条重复发消息。长期无答复的待补项保留资料，不占用必须人工清零的队列，不阻断已经可靠的部分使用。

多菜无标签场景首期仅入窗口素材。后续若要做精确配图，先单独验证区域定位与匹配；出现错配时宁可少配，不以“匹配率高”掩盖错误。商家示意图、用户实拍和原料图在消费者页面明确区分。

## 与营养和消费端的隔离

目录事实是否收录不依赖营养分析成功。只凭菜名、菜单图或一盆原料，不推导确定份量、制作油量或精确营养。已有异步营养任务复用，但只接收明确的一条目标记录及正确证据；多菜概览不直接送入单菜分析。食堂列表、详情、地图、搜索、收藏及录餐入口需统一处理无实物图、价格单位未知和营养未知，不用空值冒充零值。

## 用真实样本验证边界

第一步使用本次紫荆园25张去重照片和清芬园材料建立可追溯的预期结果。只标注图片实际支持的事实；无法确定的包子馅料、碗规格、单位必须以未知作为正确答案。人工标注样本是一次性评测成本，不应变成每批运营工序。

第二步安排少量窗口按 v1.0 重新采集，建议覆盖普通文字菜单、轮播屏、套餐、自选计价及多菜实物。对照旧拍法和新拍法的总耗时，区别“新增现场负担”与“减少后台劳动”。同一张图片的副本和同一窗口近似照片不能分到训练优化组和独立验收组冒充泛化效果。

第三步用未参与规则调优的窗口及不同手机、光线独立验收。试采规模先求覆盖类型，不用25张旧照片宣称普遍准确率。样本有限时同时给出记录数、错误数和逐项结果，不只报一个百分比。

## 建议验收目标

以下供讨论确认，不是当前实测成绩。每类菜单单独计算，不能靠简单菜单平均掩盖难例。

| 指标 | 统计口径与建议门槛 |
| --- | --- |
| 后期人工耗时 | 每100个有效条目的离场后整理、追问、配图和纠错分钟数；建议比人工基线下降至少70% |
| 总人工耗时 | 加上现场拍摄、自检和补采；必须下降，不能只把劳动转嫁给采集者 |
| 无人工处理比例 | 符合协议且在支持范围的条目中，无逐条编辑或追问即可可用的占比；建议达到80%以上再扩大 |
| 可见条目覆盖 | 可读菜单上应提取条目的召回与漏行数；必须和自动通过准确率一起报告 |
| 关键错误 | 错窗口、价格行错配、猜单位、套餐价误分、错图关联；试采放行集发现即修复并回归，不只看平均分 |
| 运行与费用 | 每窗口处理费用、预检和完成耗时的中位数与慢端、重试率、上传失败恢复率；试验后再定预算 |

覆盖率的分母包含应有却漏掉的条目；无人工处理率也应计入拒绝、失败和未解决项，防止只统计成功结果。零人工与正确率要同时成立，不能靠不生成困难条目获得虚假的高自动化率。

## 关键测试样例

重复提交不重建；旧任务不覆盖新版本；多人同时纠错触发冲突；学生上传不越权；菜单价无单位保持未知；两荤一素6元不赋给所有菜；水果捞三档不擅自命名小中大；原料不当成品；无标签多菜不强配；宣传图不当实拍；同窗重复菜单候选合并、异窗同名保留；缺页不判停售；旧照片不变最新价格；无图无营养记录可正常展示。

## 分阶段改造与影响范围

### 第一阶段 验证协议和提取闭环

先做最小离线或隔离环境试验：真实素材输入，输出带证据的菜单草稿和具体疑点，测人工处理时间。必须先证明“按规范拍能够省后期人力”，再把流程铺到更多采集者。此阶段不接生产写库，不要求完善任务认领或自动结算。

### 第二阶段 接入正式采集链路

改小程序素材会话、高清上传、草稿恢复、预检反馈与一次确认；后端增加会话、素材及异步提取；Admin只处理例外和抽检。复用目录、权限和版本发布服务，保留普通单菜上传。菜单无实物图作为正常情况适配所有消费入口。数据库变化先改 DO 与幂等迁移，经目标库核对和授权后执行。

### 第三阶段 扩大自动处理边界

根据试验增加标签同框、多菜区域对应、复杂组合和跨批更新识别。任务认领、进度与贡献记录有实际规模后再产品化；结算保持独立授权与审计，不由模型自行决定金额。

## 建议本次讨论优先确认的三点

1. 首期以文字菜单、清晰图文菜单和明确售卖规则为自动化主线；无标签实物只留素材，不强配。
2. 试采先用整批确认，达到独立样本门槛后对支持类型开放自动通过，平台只处理抽检和冲突。
3. 用总人工时间和后期人工时间共同验收；合格素材算法处理失败优先改系统，而不是不断加重采集要求。

这样才能让采集标准落在算法可稳定处理的范围内，并且通过数据决定下一步扩到哪里，而不是用更严格的拍摄要求掩盖后端仍然大量人工处理。
