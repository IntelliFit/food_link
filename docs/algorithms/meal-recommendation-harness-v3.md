# 餐食推荐 Harness v3：让已有数据形成可执行的一餐

## 范围

本轮沿用 Go 原生有界工具循环，改进数据检索、对话状态与结果校验，不更换模型供应商，不接入库存、配送或实时外卖平台，不修改数据库结构。目标数据仍是公共食物库和食物地图里的已有餐食、学校与商家信息。

## 已实现的规则

1. **所在地和食堂可用性分开。** GPS、常用学校、学生身份都不自动授权校园餐。用户明确说明能在某校食堂吃饭后，才将该校校园候选作为可执行推荐。简短“可以”绑定刚刚追问的学校；明确拒绝校园则只查商家。更换学校/出差清除旧可用性，保留本餐预算和忌口。
2. **本餐硬条件归用户控制。** 场景、距离、预算、忌口不能被模型的检索参数偷偷改写。检索时临时尝试的蛋白/热量阈值不成为以后各轮的硬限制。“虾今天可以吃了”仅解除临时虾忌口，花生继续保留；档案过敏限制不会随口味调整解除。鸡肉与常见鸡胸/鸡腿/鸡饭、海鲜与鱼子等文本关联纳入筛选。
3. **原始证据可见。** 近30天记录天数、条数、常见食物次数由服务端统计并显示，不再因为模型文本里带数字就连真实历史证据一起消失。模型自由文本仍拒绝未经核验的数字、疗效与过敏安全承诺；菜品价格/营养以服务器卡片展示。记录不等于完整实际摄入。
4. **一餐可以由真实条目组合。** 新增 `compose_meal` 工具，以同一食堂或同一明确地址商家的2–4个条目、各一个库内记录份量核算总价与营养。按重量/个数计价且无法核实一份的条目不直接当作整份；检查整餐预算、营养限制、忌口和主食/蛋白结构。该结构检查是工程门槛，不是饱腹或医学保证。
5. **组合不丢失来源。** 组合 ID 不进入数据库 UUID 查询；详情与位置追问展开为原始条目并重新查询。前端展示组成、价格和各自位置，点击组合后选择其中一道打开原食物详情。模型失败时保留已验证可行的完整餐候选，标注数据库降级且不扣推荐积分。
6. **目录关联增强，但不捏造位置。** 附近检索在既有目录 ID 外支持仅有准确学校名的旧记录关联，校园分类同时识别 `is_campus_food` 与 `type=campus`。距离仍是近似直线距离，学校级定位不会被展示为店铺精确定位。没有可定位/可核算商家时说明数据覆盖不足，不声称当地没有店。

## 线上截图回归：外卖范围、否定场所与诚实的覆盖说明（2026-10-17，未发布）

线上对话里，用户在家要外卖，Agent 却给出“AI原点社区食堂（名称待确认）”的菜；用户说“食堂不是外卖，继续推荐其他的”仍是同一家；随后的抱怨和“我就是需要附近商家的呀，你给我点呗”被交给普通对话，普通对话编出“只能看到校园食堂的数据，没有接入外卖平台”。原因是下面四处判断，均已在本地代码中修复并有回归测试：

7. **外卖范围不含食堂。** 目录把一部分食堂（社区、公司食堂）存成了“商家”记录，原先只按 `is_campus_food` 区分。现在 `domain.IsCanteenVenue`（校园菜、带食堂名的记录，或商家名含“食堂”）在外卖场景下一律排除，只有用户点名那一家时才保留。
8. **用户否定的场所不再重复推荐。** “X不是外卖”“别再推荐X”“我不去X”被解析成被拒场所，写入本餐 `ExcludedCanteens`（正锁定同一家时同时解除锁定）。“食堂”“商家”“社区”等类别词不是场所名，不会被误排除；“不要只推荐X”不算拒绝。
9. **对推荐结果的抱怨和追问仍在餐食对话里。** 推荐之后，同时带有纠正/要求语气（“不是”“我都说了”“还在”“我就是”“你给我”……）和餐食名词（食堂、商家、外卖、店、推荐、换……）的话继续进入 Agent；与饮食无关的抱怨、明确换话题仍进入普通对话。小程序 `isMealFeedbackOnRecommendation` 镜像同一口径，使“预计消耗”与服务端一致。普通宠物对话看不到餐食库，提示词新增一条：不得声称“只能看到校园食堂的数据”“没有商家数据”或能替用户下单，用户要推荐时引导其直接说出需求。
10. **没有可推荐的外卖商家时，说清楚有什么、排除了什么。** 回答给出范围内已收录商家和菜品的数量、被排除的食堂，并说明“这不代表当地没有商家：没有接入美团、饿了么这类外卖平台的实时数据”，不再重复一句泛泛的追问。附近商家都已推荐过或被排除、模型交不出选择时，也返回这段说明，而不是“这次没能完成餐食分析，可以重试”。商家目录本身很小（一次只读抽查：某居民区 5 公里内约 68 家，多数每家 1–3 道菜，不少没有价格），这是数据覆盖问题，不是算法能补出来的。

## 同食堂搭配、聊天曝光轮换、练前练后与免费确认（2026-10-17，未发布）

11. **推荐的单位是一餐：服务端在同一食堂里搭配。** 搜索回合（`CompleteMeal` 恒为真）里，`search_*` 工具用已检索的菜单枚举“主食+荤菜（可再加蔬菜、汤或第二道荤菜）”或“整份主餐+配菜”，作为 `meal_plan` 候选与单品一起进入同一套范围、忌口、预算、热量和营养门禁及排序（`mealBuildCombinations` → `searchMealOptions`）；模型仍可用 `compose_meal` 自己组合。
    - 零件只取份价已知的单品（单位为 份/碗/盘/套/套餐/餐/例）；没写单位、按两/按个/按串计价的不拼。披萨、薯条、冰品、饮料不是餐的零件；涮羊肉、麻辣烫、冒菜、串串香、荤豆花等因锅底和必选费用不明，不当作可单点的餐。
    - 在同一食堂（或同一明确地址的商家）内搭配，窗口可以不同：已知楼层必须一致，至多 3 个窗口；披萨、火锅、烧烤、饮品等特色档口的菜只能自成一餐。需要到不同窗口购买时，卡片的组成里分别写明各道菜的价格和窗口。
    - 同一道菜在两个窗口出售算一道菜：一餐里不会出现两次；多个方案之间、以及本对话里已推荐过的菜，也按菜名判断是否重复。
    - 排序沿用同一套引擎：先看营养贴合度，只有贴合度在当前最高分 5 分以内的组合才比较多样性（同一道菜、同一食堂、同类蛋白在同一答案里互相扣分；近期推荐过的菜扣分，主食不扣；价格超过 25 元、多跑一个窗口小幅扣分）。这些扣分不能把组合抬出营养带；贴合度低于 50 的“一餐”（例如整只烤鸭）不推荐。
    - 没有可搭配时如实说明原因（没有标份价、缺主食或荤菜、条件太严），不编价格。
12. **识别规则按真实菜单修正。** 面、抄手、粉等带浇头的碗，记录蛋白不少于 15g 时算整份主餐；“元/例”算一份的计价单位（北大食堂大量使用）；面、饭、粥、饼归主食；窗口名含“素菜”的菜归蔬菜。
13. **聊天也有近期推荐记忆。** 每次聊天给出的推荐（整餐及其中每道菜）以“已展示”写入已有的 `meal_recommendation_memory`；之后无论首页还是聊天，营养贴合度相近时优先没展示过的菜，规则回退的选择同样轮换。读取一次、写入有 2 秒上限，失败不影响对话；首页反馈接口不变，聊天结果不下发反馈编号。
14. **练前/练后。** 用户说“一会要健身”“准备去跑步”“练前”（pre）或“刚练完”“游泳后”“打完球”（post）时，只调整这一餐的宏量区间：练前偏碳水、少油、份量不要太大；练后蛋白和碳水都要足。明天、周末等其他日子的训练、健身房/运动鞋等词不算；不改长期目标，不按运动热量等量补吃；“不练了”取消。比较工具与排序使用同一份约束，所以分数一致。这是工程容差，不是运动营养处方。
15. **推荐刚结束时的纯确认免费收尾。** 紧跟在有选项的推荐之后、不带其他内容的“谢谢”“就这个吧”“我去吃饭了”，用一句固定回复直接收尾，不调用模型、不扣积分、不要求已有饮食记录（`billing_status=free_acknowledgement`），对话照常保存，且不结束这段餐食对话（之后的“换一批”仍属于餐食）。中间插入其他话题、推荐卡只是澄清问题、新会话里的这类话，仍走原有路由；上一条回答以问号结尾时，单独的“好的”多半是在回答它，也不拦截。小程序 `pet-chat/meal-routing.ts` 镜像同一判定（两端测试用同一批句子），确认显示预计消耗 0。

## 代码评审后的修正（2026-10-18，未发布）

16. **说“保留”不再被当成“拒绝”。** “还是推荐桃李园吧”“一直推荐桃李园就行”“不用推荐桃李园以外的”不再把该食堂排除；只有“还在/又在/老是/怎么还推荐X”这类抱怨、或“X不是外卖”“别再推荐X”才算拒绝，并去掉“我都说了”“你推荐的”等前缀只留场所名；“X不是外卖吗？”是提问，不算拒绝。
17. **对推荐的反馈要提到吃饭的地方或推荐本身。** 必须同时有纠正/要求语气和“食堂、商家、外卖、店、餐厅、推荐、附近、这家”等词；“我需要多吃蛋白质吗”“我最近一直在吃外卖，会不会长胖”“你别管吃的了”仍交给普通对话。小程序同步。
18. **提问不是确认。** “就这个？”“嗯？”“好吗”不走免费固定回复（“在吗”除外）；“好麻烦了”不再当作致谢。两端都只保留汉字、字母和数字再判断，表情、全角空格、各种标点处理一致。
19. **明确要外卖时，说出的地点只是所在位置。** “我在AI原点社区，想点外卖”不会锁定该社区食堂；“不想去食堂/学校”等同于不要校园餐。“饭堂、职工/员工/学生/教工/社区餐厅、名称待确认”的商家记录也按食堂处理。
20. **覆盖说明只说测到的事实。** 只在本轮确实做过外卖检索时给出；同一轮多次检索累计；刚推荐过的商家会点名说明“都推荐过了”，而不是说附近没有商家；同一食堂只列一次。
21. **练前/练后更谨慎。** “刚打完饭/打完卡/打完电话/旅游完”“练车/练字/练习”“没时间运动”不算训练；换到另一餐（午餐→晚餐）时清除上一餐的训练时机。
22. **组合细节。** “可乐鸡翅/可乐排骨”是荤菜不是饮料；“鱼香茄子、鸡毛菜、贝贝南瓜、牛油果”不算荤菜；有一道菜供应时段未知时，整餐也标为未知。大菜单下双荤搭配只取每道主菜之后蛋白密度最高的6道和最清淡的6个蔬菜，每道菜的角色只算一次：12个食堂、2184道菜的检索从约0.69秒降到约0.21秒，真实食堂单次5–19毫秒，结果不变。
23. **聊天记忆不拖慢、不打扰首页。** 写入放在“完成”事件之后（客户端离开也不中断，2秒上限）；不记录主食；首页卡片自己选中的那道菜不记录，避免首页因此换掉它。普通宠物对话提示词新增：不得声称“只能看到校园食堂的数据”或能替用户下单。

## 真实模型回放后的修正（2026-10-18，未发布）

用真实模型、只读数据库、内存会话（不写库、不扣积分、合成测试用户）回放了截图对话和 4 组连续对话，发现并修正：

24. **回答文字与卡片不一致。** 模型的选择不在营养/多样性范围内时，引擎会换掉选项，但原先仍沿用模型的文字，其中用自己的话提到了卡片上没有的菜（如“吉旺角茶餐厅的牛肉滑蛋饭套餐”），或露出引擎内部说明。现在按场所名识别这类改写；引擎换掉选项时，回答改为描述实际卡片，并先回应本轮条件（练前/练后、价格上限、已排除的场所）。
25. **复合追问和短问句掉出餐食对话。** “便宜一点，20元以内”“我一会要去健身，再推荐一下”“有汤吗”“能打包吗”“这个菜辣吗”在有推荐时继续由 Agent 回答；“我需要多吃蛋白质吗”“我吃肉会胖吗”仍是普通对话。小程序同步。
26. **“我就是需要附近商家的呀”把外卖变成了不限场景**，混入了校园菜。现在“要/找/推荐……商家/店”“附近的商家”都按外卖处理（同时提到食堂的除外）。

27. **模型在“近优”范围内自由选择，不再被整组推翻。** 原规则要求模型的每个选择都落在最优 5 分以内、且必须是当步“最不重复”的那一个，否则三份全部换成引擎的答案——真实回放中几乎每轮都被推翻，回复变成模板。现在：
    - 硬条件不变（预算、热量、忌口/过敏、排除的场所、能点成一餐）。
    - 营养上只要求“近优”：与本轮最优相差不超过 10 分（引擎自己选仍用 5 分）。
    - 多样性只保留轻规则：不重复同一道菜；有新鲜的近优选项时不选近期推荐过的；有其他类型的近优选项时，三份里同一类主食不超过两份。
    - 不合格的只替换那一份（用引擎剩下的最优项补上），模型的其他选择和它的说明保留。
    - 检索结果给每个选项标 near_best，提示词告诉模型：在 near_best 里按用户这轮的口味、距离、价格自由取舍并说明理由。

回放结果：截图四轮全部由 Agent 回答、场景始终是外卖、只出现商家、已排除的食堂不再出现、文字与卡片一致；连续调整（换一批、20元以内、一会健身、谢谢、就这个吧）和换食堂、混合话题都按预期进入对应流程。本机经远程数据库检索较慢（单次 2–24 秒，单轮 23–43 秒），远程连接偶有断开导致个别轮次超时；生产环境数据库与服务同机房，耗时需在线上另测。

## 规则只做快速初筛，拿不准的交给模型（2026-10-18，未发布）

28. **分流：规则先判，拿不准的问模型。** 规则认识的说法照旧直接分流；规则不认识、但这段对话正在谈餐食或这句话提到吃的，就请模型判断“是否属于餐食对话”（3 秒上限，失败按规则结果）。模型只能把一句话判入餐食对话，不能判出，所以实际扣费不会超过发送前显示的价格。被模型判入的那一轮，之后在服务端和小程序里都按餐食对话延续（服务端看存储标记，小程序看是否有推荐卡片）。
29. **模型选错时先让它自己改。** 模型的选择不在“近优”范围或违反多样性时，先把原因和可替换的近优选项告诉模型，让它改一次；改完仍不合格，才由引擎替换不合格的那一份。
30. **确认类回复由模型结合卡片来写。** “就这个吧”“谢谢啦”由模型根据屏幕上的推荐写一句自然的回应（如说出选的是哪一份、在哪里买），仍然免费；模型不可用、超时或写了数字/价格/长段文字时用固定回复。
31. **没有合适结果时由模型解释。** 外卖检索把覆盖范围（范围内商家数、已推荐过的商家、被排除的食堂、没有接入外卖平台）交给模型，由模型如实说明并给下一步；过滤掉无依据的数字，声称“只能看到校园食堂”、替用户下单、或在已有定位时追问位置的，改用固定说明；外卖场景总会说明“这不代表当地没有商家”。
32. **模型可以按原话更新更多条件。** 除忌口、偏好、食堂、份数外，模型还能按用户原话设置练前/练后（引用的原话须与运动有关）和外卖/食堂场景（原话须与地点有关），补上规则没覆盖的说法，例如“待会儿要去打场羽毛球赛”“我在家不想出门”。
33. **价格未知时不因“费用未确认”拒绝。** 外卖商家大多没有收录价格，模型如实标注“必选费用未确认”后，原先会把它自己的每个选择都拒掉。现在只有“不能直接点单”一定拒绝；“费用未确认”只在卡片会显示价格时拒绝。
34. **模型没完成时，先用本轮已查到的合格选项。** 模型调用超时或几次都没选出合格项时，如果本轮检索已经找到符合条件、且不是刚才那张卡片上的选项，就直接给出（标注“AI 解读暂不可用”），并把用户刚说的口味（辣/清淡/酸/甜）排在前面；都没有时才提示重试。
35. **只替换了一部分时，回复按卡片逐项说明**（保留的用模型的理由，补上的只写名称），补位只用近优且未被拒的选项。

## 仍须明确的边界

- 自然语言条件解析是保守的规则与工具协作，不代表所有中文表达均已覆盖；检索失败和模型选择失败需分别统计。
- 食品配料及交叉接触信息不完整，文本筛选不等于过敏安全，不能承诺不含某过敏原。
- 已有商家缺少坐标、可关联目录或份量价格时，算法不能凭空补齐。下一步数据治理重点是这些已有字段的核验，不是库存/配送集成。
- 原始评估从未确认校园可用性，因此修复后的原脚本可能只得到澄清，不应用“有菜率下降”认定修复失败。确认可用后是否能选餐，应看新增连续对话评估。
- 用户口述的所在地（“我现在在北大”）与 30 分钟内的定位冲突时，仍沿用上游规则：没有提到食堂就以定位附近检索为准；未改。
- 加餐、零食、水果、饮品的单独请求仍按“一餐”处理（上游规则，搜索回合恒要求完整一餐），可能得到“没有完整一餐”的回答；需要产品决定是否增加加餐模式。
- 目录里同一个社区食堂曾存了两份（带窗口的食堂记录 + 135 条“AI原点社区食堂（名称待确认）”商家副本）。2026-10-18 经用户同意已在线上库合并：与食堂记录同名的 114 条和 7 条名称/热量不可信的拍照记录软删除（status=deleted，可恢复），14 条加购项移入食堂记录；改前备份了全部 135 条。代码仍会把这类副本识别为食堂。
- 没有外卖平台的实时数据、库存和配送；商家目录很小，覆盖不足时只能如实说明，不能替用户下单。
- 组合的角色（主食/荤菜/蔬菜/汤）按菜名与窗口名识别，是启发式；识别错误只会让某些搭配缺失或不够自然，不会绕过整餐结构、价格和营养校验。不吃主食的低碳搭配暂不组合。
- 组合按各 1 份记录价格合计，实际份量、供应、排队和配料需向窗口确认；跨窗口只保证同一楼层、不超过 3 个窗口，不评估步行或排队时间。
- 练前/练后的区间是工程容差；“一会”之类时间词只判断是否即将训练，不判断具体间隔。
- 聊天路径的近期推荐记忆依赖 `meal_recommendation_memory` 表已存在；没有该表时退化为无记忆排序。
- 免费确认与小程序预计消耗按同一批句子判断，句式变化需两端同步修改；未覆盖的说法会进入原有路由，用户重述即可。
- 当前未部署、未迁移数据库，也未启动/重启本地前后端。具体测试结果与失败样本见本轮评估报告，不以 Go 命令 PASS 代替推荐质量结论。
