# 餐食推荐 Harness v3：让已有数据形成可执行的一餐

## 范围

本轮沿用 Go 原生有界工具循环，改进数据检索、对话状态与结果校验，不更换模型供应商，不接入库存、配送或实时外卖平台，不修改数据库结构。目标数据仍是公共食物库和食物地图里的已有餐食、学校与商家信息。

## 已实现的规则

1. **所在地和食堂可用性分开。** GPS、常用学校、学生身份都不自动授权校园餐。用户明确说明能在某校食堂吃饭后，才将该校校园候选作为可执行推荐。简短“可以”绑定刚刚追问的学校；明确拒绝校园则只查商家。更换学校/出差清除旧可用性，保留本餐预算和忌口。
2. **本餐硬条件归用户控制。** 场景、距离、预算、忌口不能被模型的检索参数偷偷改写。检索时临时尝试的蛋白/热量阈值不成为以后各轮的硬限制。“虾今天可以吃了”仅解除临时虾忌口，花生继续保留；档案过敏限制不会随口味调整解除。鸡肉与常见鸡胸/鸡腿/鸡饭、海鲜与鱼子等文本关联纳入筛选。
3. **原始证据可见。** 近30天记录天数、条数、常见食物次数由服务端统计并显示，不再因为模型文本里带数字就连真实历史证据一起消失。模型自由文本仍拒绝未经核验的数字、疗效与过敏安全承诺；菜品价格/营养以服务器卡片展示。记录不等于完整实际摄入。
4. **一餐可以由真实条目组合。** 新增 `compose_meal` 工具，以同一食堂或同一明确地址商家的2–4个条目、各一个库内记录份量核算总价与营养。按重量/个数计价且无法核实一份的条目不直接当作整份；检查整餐预算、营养限制、忌口和主食/蛋白结构。该结构检查是工程门槛，不是饱腹或医学保证。
5. **组合不丢失来源。** 组合 ID 不进入数据库 UUID 查询；详情与位置追问展开为原始条目并重新查询。前端展示组成、价格和各自位置，点击组合后选择其中一道打开原食物详情。模型失败时保留已验证可行的完整餐候选，标注数据库降级且不扣推荐积分。
6. **目录关联增强，但不捏造位置。** 附近检索在既有目录 ID 外支持仅有准确学校名的旧记录关联，校园分类同时识别 `is_campus_food` 与 `type=campus`。距离仍是近似直线距离，学校级定位不会被展示为店铺精确定位。没有可定位/可核算商家时说明数据覆盖不足，不声称当地没有店。

## 验证方式

- `meal_recommendation_policy_test.go`：位置/身份与权限分离、部分忌口解除、否定范围、换地点、模型条件漂移、历史数字、鸡肉/海鲜匹配、整餐组合、总价、组合详情和查询 ID 门禁。
- `diet_nearby_repo_test.go`：真实 SQL 查询覆盖半径、预算、屏蔽关系、目录坐标、仅学校名旧记录及校园类型不能冒充商家。
- 既有校园工具用例补充“已确认可用”的前提；不再用学生身份代替食堂可用确认，原营养/预算/工具调用断言保留。
- 原五场景20轮评估脚本不变，另加清华/北大/商家测试点/无GPS/中途换学校的五场景20轮。真实用户档案和记录只读，模拟聊天仅内存，不扣用户积分；报告匿名化，公开构造的测试位置不冒充真实用户位置。
- 微信静态与 Jest 交互测试覆盖组合明细跳转、取消、已有对话与定位流程。微信开发者工具导航/截图仍需正确项目处于运行状态，静态测试不能代替运行时验收。

## 仍须明确的边界

- 自然语言条件解析是保守的规则与工具协作，不代表所有中文表达均已覆盖；检索失败和模型选择失败需分别统计。
- 食品配料及交叉接触信息不完整，文本筛选不等于过敏安全，不能承诺不含某过敏原。
- 已有商家缺少坐标、可关联目录或份量价格时，算法不能凭空补齐。下一步数据治理重点是这些已有字段的核验，不是库存/配送集成。
- 原始评估从未确认校园可用性，因此修复后的原脚本可能只得到澄清，不应用“有菜率下降”认定修复失败。确认可用后是否能选餐，应看新增连续对话评估。
- 当前未部署、未迁移数据库，也未启动/重启本地前后端。具体测试结果与失败样本见本轮评估报告，不以 Go 命令 PASS 代替推荐质量结论。
