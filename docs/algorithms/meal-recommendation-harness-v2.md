# 餐食推荐 Harness v2

## 目标与技术选择

2026-09-26：在现有 Go 服务内实现 `foodlink-meal-harness-v2`，复用宠物聊天会话、SSE、模型网关、计费和工具接口；本次没有安装 Eino、LangGraph 或引入 Python Agent 服务。

问题不是缺少框架名称，而是旧链路只读取当天数据、没有 GPS 检索，以及模型最终选择被确定性组合覆盖。新 Harness 保留可校验的模型选择，让程序负责权限、真实数据、边界与失败兜底。

参考：[Anthropic 的 Agent 构建原则](https://www.anthropic.com/engineering/building-effective-agents)、[工具与反馈设计](https://www.anthropic.com/engineering/writing-tools-for-agents)。Eino ADK 可作为后续复杂任务编排的选择，但不是当前接入历史和位置数据的前提。

## 执行链路

1. HTTP 接收本轮问题、同餐会话、首页建议上下文及可选定位，验证位置有效性。
2. 读取个人证据：健康档案、近 30 天具体餐食与食物频率、最近 7 天运动、今日摄入与营养目标。
3. 模型用工具维护临时偏好并检索指定学校或附近餐食；可继续查询详情、比较和重新检索。
4. 程序验证模型返回的 1–3 个菜品 ID、价格/营养限制、已知过敏信息与本轮忌口。无效选择反馈给模型修正，不把任意文本当成真实菜品。
5. 返回解释、数据库卡片、数据边界和检索依据；缺位置/数据时追问。模型或检索异常明确区分，降级或澄清不收推荐积分。

工具：`get_meal_context`、`set_meal_preferences`、`search_nearby_foods`、`search_campus_foods`、`get_campus_food_details`、`compare_campus_foods`。模型循环最多 6 轮、10 次工具调用，主流程超时 45 秒。

允许模型先提取本餐偏好；若迟迟不检索，第 3 轮明确指定检索工具。最后一轮保留给最终解释，并从请求中移除工具定义，避免兼容网关忽略 `tool_choice=none` 后继续调用工具。选择非法 ID 会获得校验反馈并可重试。

普通非选餐聊天保持原来的聊天链路；自炊问题不强行套用附近菜单。首页仍是免费的紧凑基础建议卡，不自动定位、不自动发消息。

## 证据与约束

- 30 天按实际记录天数计算均值，不把没记录视为没吃。保留最近 18 餐和最多 30 种食物频率，最近重复餐食在候选排序中降权；常吃不等于喜欢。
- 当前明确需求覆盖长期目标，但“刚训练完”不自动改写为长期增肌，也不按运动消耗等量补吃。
- 同一会话保留预算、忌口和口味；模型可补充条件，不能自行删除档案过敏信息，不能为凑结果扩大用户距离限制。
- 验证后的模型选择及个性化原因保留，不再无条件改写为固定的三道组合。
- 模型解释不承担数值来源。数值与位置来自卡片；自然语言中未知数值、常见无依据功效/用油/过敏保证被过滤，过滤后没有有效理由时显示核对配料的保守提示。这不是完整的语义真实性证明，仍需持续抽检。
- 过敏处理仍基于现有菜名/配料文本匹配；未建设完整的结构化配方和交叉接触核验体系，因此必须提示向商家确认，不能承诺过敏安全。
- 不持久化用户定位，不输出到日志。位置只在页面内存和本轮请求内，30 分钟过期；允许用户清除和刷新。

## 附近数据的真实范围

数据来自 `public_food_library` 已发布条目，使用餐食 → 食堂 → 校区 → 学校坐标逐级回退。应用和现有食物地图采用 GCJ-02；查询使用小范围平面直线距离近似，默认 3 km、最大 10 km。不需要新增表或 PostGIS 扩展。

GPS 附近模式可跨学校，不把第一道菜所属学校误当为整个搜索学校。明确指定学校时使用该学校；无定位时可以使用用户指定/常用学校，但不把常用学校位置假装成当前位置。外卖场景仅检索带商家名称的非校园条目。

这不是实时外卖平台接入：没有美团/饿了么实时菜单、库存、营业状态或配送范围。学校级定位仅代表大致范围，不能保证访客可进入。记录中的价格、配料和营养也不等于实时或人工核验数据。

## 验证入口

后端：

```sh
cd backend
go test ./internal/health/service ./internal/pet/handler -count=1
go test ./internal/health/repo -run TestNearbyDiet -count=1
```

覆盖：历史时间范围、重复降权、预算/忌口过滤、数据库距离与坐标回退、屏蔽关系、模型未知 ID 纠错、模型选择保留、免费澄清、检索失败、HTTP 上下文透传。

前端：`meal-location`、`pet-diet-recommendation`、`pet-chat-stream`、`pet-chat-credit-cost`、`pet-chat-settings-entry`、`pet-chat-latest-message`、`pet-navigation`、`next-meal-guidance` 对应的 Jest 测试。

实网测试 `TestMealHarnessLivePersonalizedNearby` 默认跳过，需显式设置 `FOODLINK_RUN_MEAL_HARNESS_LIVE=1`。使用合成健康/饮食/运动上下文、真实清华附近已发布餐食和配置的真实模型；会产生模型 API 用量，但不写入用户聊天、不扣用户积分、不迁移数据库。

微信运行时验收需用户运行 `npm run dev:weapp` 并打开正确的 `apps/wechat` 项目。不得用旧 `dist` 或另一个小程序的截图替代本次验证。

## 本轮实测记录

最终静态与自动化门禁通过：微信 TypeScript、目标 ESLint、8 个 Jest suites / 28 tests；Go health/service 与 pet/handler 全包、附近 repo 定向用例、对应三包 `go vet`、app 编译和目标 diff check。

2026-09-26 真实模型与数据库联调：使用清华附近坐标和合成个人资料（此前鸡肉饭、力量训练、花生过敏），问题为“我刚做完力量训练，今天不吃鸡肉，附近有什么清淡的饭可以选？”。

- 两次修正后的实网测试通过，分别约 20.30 秒、21.85 秒；均为 6 轮模型、6 次工具调用，保留模型最终选择。
- 首次搜索不足/为空后继续搜索，再比较并收敛；真实候选示例为铁板滑蛋龙利鱼饭（约 1.12 km）、柠檬酸汤鱼（约 1.74 km）。距离只针对测试坐标，不代表用户当前位置。
- 两次都没有写入真实用户记录或扣用户积分。此结果验证链路可运行，不是多用户准确率/延迟基准。
- 实测曾出现“酸汤避免重油”“缓解疲劳”等过度推断，已增加对应输出过滤与回归断言；过敏数据不完整的限制仍保留。
- 微信工具已尝试指定 `D:/files/food_link/apps/wechat` 验证，但项目没有可用 runtime，指定项目导航失败；共享自动化实例实际是另一个项目，旧 `dist` 日期为 2026-09-15。未启动用户的 watch，因此没有本轮运行时 UI 截图。代码尚未部署、上传或发布。
