# 补剂服用记录同步圈子

补剂摄入使用独立的 `supplement_intakes` 数据源，圈子直接读取记录，不额外创建圈子帖子。动态类型为 `supplement_intake`。

新记录保存并通过内容审核后，按现有公开资料、好友关系及拉黑规则出现在圈子。列表和详情展示实际服用时间、品牌、产品图片、名称、剂量及本次成分含量；成分含量为每份快照含量乘以服用份数。列表最多展示三项成分，详情展示全部及多张瓶身/标签图；点击图片预览原图。未填写品牌不虚构品牌，缺图或图片失败使用胶囊图形。不把补剂显示为餐食，不显示无意义的零热量、蛋白质等餐食摘要，也不从新瓶身标签回填历史营养快照。

私人备注不随动态返回。数据库升级前已有的摄入记录默认隐藏，防止此前的私人记录因升级自动公开；新记录由服务显式写入 `hidden_from_feed=false`，仍受资料公开设置约束。

历史恢复通过显式迁移命令执行，须先获目标库与恢复范围授权。先使用 `go run ./cmd/migration -config-dir . -restore-supplement-feed -restore-before <RFC3339截止时间> -restore-run-key <审计标识>` 只读查看范围；加 `-restore-apply` 才执行。可用 `-restore-exclude-ids <逗号分隔ID>` 排除已知作者隐藏的记录。仅恢复截止前、资料允许公开、没有举报、内容审核通过的记录；私人账号及审核失败的记录保持隐藏。恢复只改可见性，不改变服用时间、快照、数量或营养统计。独立迁移 DO 定义的 `supplement_feed_restorations` 记录每条成功恢复，重复执行不会覆盖作者后来再次隐藏的选择。该数据修复不参与普通迁移或后端启动，小程序尚无批量历史补发 UI。

支持补剂筛选、详情、点赞、评论、互动通知及举报处理。作者可从圈子隐藏动态，保留营养统计；删除服用记录会移除对应动态并通知首页刷新。补剂柜新增和删除服用记录时通知圈子刷新。补剂快照不可在圈子编辑。

## 发布顺序

### 产品资料快照（2026-10-10）

`SupplementIntakeDO.ProductSnapshot` 为可空 JSONB，包含 `brand`、`image_urls` 和资料来源。新摄入保存服用时品牌及最多三张图片，并与名称/规格/成分一并通过发布内容审核；后续补剂柜修改不改变旧动态。Feed 返回 `supplement_product`，不查询当前补剂柜，也不公开备注、条码或服用计划。

部署此版后端前，先获得目标库迁移授权并从 `backend/` 执行 `go run ./cmd/migration -config-dir . -only-supplement-feed-product`。该模式仅增加上述可空列，重复运行安全，不补发动态或修改营养账本。

已有记录的产品资料须显式补齐：在同一命令加 `-supplement-product-before <已过去的RFC3339时间>` 试算，加 `-supplement-product-apply` 才审核并写入。只处理快照为空、当前可见、资料公开且无举报的记录；同作者同补剂、名称/每份规格/成分必须完全一致，补剂柜条目自该服用记录创建后不得编辑。审核包含品牌和全部图片；失败或审核期间编辑/隐藏则保留原记录。只写产品快照，标记 `source=cabinet_match`，不改摄入时间、份数、成分、备注或可见性，重复执行不会覆盖已有快照。没有品牌/图片或无法可靠匹配的记录保持缺资料。

首次上线基础补剂动态时，确认并获得目标非本地数据库迁移授权，再在 `backend/` 运行（已经完成此迁移的环境不重复执行）：

```powershell
go run ./cmd/migration -config-dir . -only-supplement-feed
```

该迁移新增 `SupplementIntakeDO.HiddenFromFeed`，并更新四张互动表的稳定命名 target type 约束。重复执行安全；不依赖手工 SQL 修库。常规全量迁移也使用同一份字段与 target type 定义。

迁移成功后再发布后端，最后上传包含新卡片和筛选的小程序及发布后台。后端服务启动时不自动迁移；旧结构部署新版后端会导致圈子查询缺列。基础补剂动态已于 2026-10-09/10 上线并完成授权范围内的历史恢复；2026-10-10 产品资料增强的迁移及发布尚待本次确认，进展见 `.local-state/current-task/supplement-product-20261010/REPORT.md`。
