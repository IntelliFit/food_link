# APP 事件通知与验收（2026-11-05）

## 范围

本批新增「私信提醒」「分析完成提醒」，默认关闭、遵守总开关及免打扰。保留本机三餐提醒，不购买聚合平台。CoachLink 本轮只提供下面的复用设计，不修改其项目。

| 事件 | 触发与取消 | 点击去向 |
| --- | --- | --- |
| 私信 | 开启后新收到的文字/图片私信；发送前仍未读、未删、双方未拉黑 | 对应会话 |
| 分析完成 | 开启后新提交的 food/food_text 任务成功、非违规、有结果且不再等待用户补充 | 当前账号分析历史 |

通知只含通用文案与必要资源标识，不展示私信正文或健康信息；不自动记账、调用 AI 或扣积分。系统奖励消息、其他分析任务类型不在第一批范围内。

## 机制与边界

- 周期扫描持久化业务记录，复用 push_deliveries 的唯一去重、租约、重试和回执。不依赖易丢失的进程内回调，不新增消息中间件。
- 服务端维护每类启用时间。旧客户端不传新增字段时保留原值；客户端不能伪造启用时间。关闭后再开启不会补推关闭期间的旧事件。
- 设备注册 protocol_version=2 才接收新路由；旧版设备继续既有提醒。发送前复查账号、token、有效设备、偏好和业务资格。
- 私信从发送时间、分析从任务提交时间起算 24 小时有效期。分析 updated_at 会因编辑更新，不能据此延长通知期限；处理超过 24 小时的任务不再通知，仍可在历史查看。
- 免打扰内暂缓，超过有效期不补发。定时提醒优先于事件积压；大量并发会增加事件通知延迟，当前实现不是无限吞吐承诺。
- 已交给推送供应商的消息无法保证撤回；「已接受」不等于手机展示或用户看见。
- 规模限制：既有 worker 每分钟扫描后最多领取 50 条发送及 50 条回执，共用 50 秒窗口；扫描失败或耗尽窗口会跳过该轮投递。此次优先级修复不等于已完成大规模压测，推广扩量前需监控扫描耗时和队列最老等待时间。
- 本机定时提醒不需要远程网络。私信等新事件仍需要远程通道；这批代码不解决 FCM 在特定移动网络不可达的问题，也不证明荣耀通道已开通。
- Expo 点击与荣耀 intent 都检查当前登录账号；账号不匹配不导航到旧账号资源。分析页从当前账号 API 读记录，不信任通知携带的健康数据。

## 迁移与上线顺序

1. 发布前重新核对实时 dev/main 与本批补丁，不覆盖另一台电脑的新提交。
2. 本轮事件列在迁移 DO：push_devices.protocol_version（默认 1）、push_deliveries.resource_id（默认空）。本次合入的既有荣耀适配另给这两张表各增加 provider（默认 expo）；相对 dev 共四列，没有新增业务表。HTTP 启动不运行迁移。
3. 先确认实际数据库/schema及授权，再执行项目迁移命令；历史记录指向 dev/main 可能共享数据库，不能按分支假定隔离。不得把本地探针当作生产迁移已完成。
   已核对 CLI 支持 `go run ./cmd/migration -config-dir <已核对配置目录> -print-target`（只打印目标、不连接）以及 `-only-push-reminders`（真正执行推送三表迁移）。确认目标、授权与备份之后才运行后者，避免全量迁移带入其他业务结构。
4. 先后端迁移与发布，再 APP。后端通过 event_notifications_supported 暴露支持能力；旧后端时 APP 新开关禁用。
5. 构建新包前统一版本：当前基线 package.json 为 4.6.20、继承 APP app.json 为 4.6.16/code66，尚未执行版本发布同步；须确定发布号并递增 versionCode，不把这份源码视为现成新安装包。私有包真实验收后再公开发布，不将调试包直接替换官网稳定包。回滚 APP 后老客户端保存偏好不应抹掉新开关；回滚后端前评估队列中未投递的新事件。

## 验收清单

- 隔离 PostgreSQL：重复迁移、旧客户端保存兼容、启用时间、扫描去重、已读/删除/双向拉黑、退出与无效 token、免打扰、过期分析编辑不复活、私信积压不挤掉定时提醒。
- 静态与现有测试：Go 相关包、APP 类型检查、diff；不新增提交到仓库的测试文件（遵循用户本轮选择）。
- 手机：同账号私信与成功分析各一次，前台/后台/锁屏；点击冷启动和热启动；退出及切换账号后点击旧通知不串号。
- 网络：普通 Wi-Fi、移动网无 VPN 分开记录。关闭 Wi-Fi 会中断无线调试，须事先设置、离线观察、连回后读取证据，不能以 Wi-Fi 收到冒充移动网验收。
- 至少跨日观察两轮本机餐次，另测长待机；一次早餐收到不代表连续调度已验证。

## CoachLink 复用建议

复用事件协议、设备绑定、账户隔离、用户偏好、去重、重试、观测与通道适配的设计；不要共用两个产品的 token、签名、应用 ID 或数据表权限。

- 固定训练/预约时间：在用户同意后同步到本机调度，离线可提醒；取消/改期时重排并去重。
- 教练私信、预约变更、报告完成：由后端持久化事件进入可靠队列，再选择适用的远程通道；应用内消息中心保留完整记录。
- 先实现最关键两三类，默认克制、支持免打扰和分类关闭。不要以常驻轮询或强制关闭省电作为通用推送替代。
- 若目标是国内 Android 无 VPN 的可靠后台送达，仍需可达的厂商通道或聚合接入；聚合可简化代码但不能承诺免掉各厂商资质。先在食探完成端到端证据，再移植协议而非整套业务。
