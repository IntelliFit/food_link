# 产品更新通知

## 使用流程

1. 后台「系统 → 产品更新通知」填写标题、功能说明和**最低小程序版本**，保存草稿。
2. 先发布包含该功能的小程序和后端，再点击「发布通知」。填写的最低版本必须包含功能；通知编号与版本号独立，同版本可发布多条通知。
3. 用户冷启动、切回小程序或登录/退出时检查通知，按创建时间顺序逐条弹出微信原生弹窗。只有「我知道了」，无取消按钮，不能通过点遮罩关闭。
4. 登录用户显式确认后写服务端记录，同账号换设备也不会重复弹；游客确认保存在当前设备，登录后按账号重新检查。清除缓存可重置游客确认，登录用户的服务端确认不会被清除。
5. 发布后禁止改正文或重新发布同一编号；需要补充内容可「复制为新草稿」后再发布。误发可撤回，保留已确认记录及人数。

读取失败不误记已读，下次打开继续检查；确认保存失败重新显示同一条通知并提示重试。应用退出、系统取消回调、账号变化都不生成确认记录。后台草稿、撤回通知、低于最低版本的客户端不弹出。

| 位置 | 行为 | 接口 |
| --- | --- | --- |
| App 启动/前台、登录状态事件 | 查询通知并弹出 | GET `/api/product-updates`（游客）、GET `/api/product-updates/pending`（登录） |
| 我知道了 | 保存确认 | POST `/api/product-updates/:id/acknowledge` |
| Admin 系统菜单 | 草稿、发布、撤回、已确认人数 | GET/POST `/api/admin/product-updates`、PATCH `/:id`、POST `/:id/publish` 或 `/:id/withdraw` |

客户端查询带 `app_version=x.y.z`；确认 JSON 为 `{"app_version":"x.y.z"}`。按数字比较版本，不作字符串排序。通知列表响应禁止缓存，不返回管理员账号。后台需要现有管理员认证，确认接口使用 JWT 中的用户 ID；重复确认幂等。

## 数据库和上线

迁移 DO：`ProductUpdateDO`、`ProductUpdateAcknowledgementDO`；两表为 `product_updates`、`product_update_acknowledgements`。确认主键是通知编号+用户 ID，两外键使用 CASCADE；删除账号时同步清除其确认记录。没有历史回填或默认公告，不自动向真实用户发样例。

核实配置实际数据库并取得远端迁移授权后，从 `backend/` 执行：

```powershell
go run ./cmd/migration -config-dir . --only-product-updates
```

专项迁移只处理这两表及约束，可重复运行。完整迁移也包含该模型与外键，HTTP 服务启动不执行迁移。迁移须在后端部署前完成，小程序须先上传/发布支持通知的包；旧包没有通知检查逻辑，仅提高版本号不能让旧包支持弹窗。

## 定向验证

- Go `internal/productupdate/handler`：真实临时 PostgreSQL、专项迁移重复运行、草稿隔离、版本筛选、发布内容不可编辑、确认幂等、账号隔离、撤回、管理员确认人数、原用户列保持。
- Go `internal/productupdate/service`：数字版本边界。
- Jest `product-updates.test.ts`：通过真实公共请求信封解包验证确认前零写入、单弹窗、多条顺序、失败重试、账号切换、游客隔离、前台重查。
- 微信运行时验收使用 weapp-devtools；接口样例必须仅拦截本功能，保持原账号/API并恢复拦截。不发布真实通知作为截图手段。
