# 校园自动补充改用 A6 DeepSeek

## 本人选择与范围

2026-10-25 本人明确接受该第三方渠道的控制参数限制，要求先用 DeepSeek，不用价格更高的千问。仅校园 `campus_public_food` 自动补充使用独立 A6 凭证和 `deepseek-v4-pro-0813`。不改变普通食物分析、其它业务渠道和资料发布后自动触发的规则，不启动所有历史草稿。

运行时配置（仅由服务器 Secret 注入，不把实际 Key 写入仓库、镜像或日志）：

```text
CAMPUS_A6_DEEPSEEK_ENABLED=true
CAMPUS_A6_DEEPSEEK_API_KEY=<server-side-secret>
```

未启用时保留既有校园 Qwen 行为，供兼容和明确回滚使用；启用后缺凭证直接失败，不静默回到千问/万界/Gemini。普通调用仍使用原对象，校园使用请求级服务视图。

## 路由与防护

- 校园文字识别和补微量营养均使用 A6 DeepSeek，原并发多模型营养链在校园视图中替换为单模型。
- DeepSeek Pro 为文本模型：有图片的校园目录项只按已有菜名/采集文字进行估算，清除图像输入并标记 `campus_image_analysis_skipped`、`campus_analysis_basis=catalog_text_only`，不声称识别过图片。没有可用目录文字时拒绝，不擅用其它视觉渠道。
- 固定 HTTPS A6 主机和路径，禁止重定向。单次 HTTP 最多40秒，每阶段90秒，每个请求级估算器最多6次物理尝试，单副本最多2个同时在途请求，输入/响应体各1MiB。复用原有至多3次短暂错误重试，遵守 Retry-After；401等永久错误不重试。
- `max_tokens=4096`、关闭思考仅作为尽力提示；此前实测商家可能忽略，因此不把它当硬成本上限。自报输出超限只告警，不因这个数字拒绝正常内容；次数、时限、体积与并发防护仍有效。
- 校验响应模型、结束标志、JSON、既有营养门禁。上游原始错误和思考内容不进入旧日志/结果，只保留请求ID和数值usage等摘要。
- 对 AI 估算的热量做确定性4/4/9重算，并同步整份能量和审计，不改写官方标签、数据库精确值和用户值，不把缺失核心宏量补0。

## 验证

- 新增 `campus_a6_deepseek_test.go`，不改原有测试断言。覆盖独立凭证/请求视图、缺凭证不回退、usage超请求仍可用、永久错误脱敏、物理次数、Retry-After、错误模型/截断/过大响应、图片无菜名拒绝、AI热量重算与权威值保留、真实服务调用形状。
- 49个定向检查项通过，4个相关后端包编译通过，`go vet`通过。另对现已合并的 `f4d9bc77` 基线执行完整相关包复核；完整测试状态以发布回执为准，不能把定向通过称为整库测试全绿。
- 一次真实 A6 无数据库服务链路：200g熟米饭，2次HTTP调用、约22.3秒，返回准确模型ID，200g重量保持，21微量/原营养门禁及确定性能量/份量一致性通过。不是食堂实测营养、长期渠道稳定性或账单验证。

## 发布与回滚

本次实现以已在 origin/dev 和 origin/main 合入的 `f4d9bc77` 为基础。发布必须先保存源码提交，再从该提交导出无凭证构建上下文，通过标准 `npm run push-docker-ccr` 构建；回执记录实际源提交、构建归档SHA和镜像digest，不拿外层旧checkout的HEAD冒充。
