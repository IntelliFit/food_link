# 食探食堂采集项目：给另一位 AI 的交接说明

整理日期：2026年10月19日（北京时间）。用途：独立评审需求、采集规范和技术方案，不是实施授权。

## 先用一分钟理解这件事

食探希望通过付费校园采集员和学生自发贡献，建立持续补充、更新、纠错的食堂资料库。真实采集对象是某个窗口在某个时点的一组素材：招牌与环境、文字菜单、带图菜单、计价规则、可能拍到的实物。素材与菜品是多对多关系，不是一张照片等于一道菜。

现有批量页面主要省去了重复填写地点，仍要求每张图填写一个菜名。用户用真实的菜单和环境照片测试后明确否定了这个设计：它没有解决菜单拆条、套餐规则、跨图关联和后期整理的劳动。

用户最重视的是：采集规范必须刚好落在算法经验证能可靠处理的范围内，让合规素材尽可能自动成为可用数据。现场增加的动作与后期节省的劳动要一起计算，不能把后台人工变成采集员逐道录入，也不能用“AI辅助”包装全量人工审核。

## 这项任务如何发展到现在

以下是本对话的实质内容摘要，不是逐字聊天记录。没有可靠日期的早期阶段不补造日期。

1. 用户最初询问现有菜品如何上传和处理，希望校园代理乃至普通学生能快速批量贡献。学校、食堂、楼层、窗口、菜名、图片等需要区分必填与可后补；不应为缺少可选信息阻止贡献。
2. 用户补充：资料库应动态更新、允许其他用户纠错。平台无法逐条核实现场事实，默认接受用户提供的信息，同时需要来源、版本与撤销错误修改的能力。
3. 用户曾询问代码是否提交、功能是否上线，并提供找不到批量入口的截图。这说明入口、提交、上传、正式发布和实际可用性必须分开说明；当前材料不能倒推当时缺入口的确切原因。
4. 随后用户实际进入批量采集页：多选的环境照、菜单照被一一变成“第几道菜名称”的必填表单。用户明确指出，这只是多次单菜录入，不是所需的复杂素材采集处理。
5. 用户提供清华清芬园案例：少量照片包含入口、窗口、数块菜单和宣传图；有时完全拍不到实物，有时一个画面有多种实物。菜单与实物对应可能需要现场信息，不应假设自动知道。
6. 用户又提供“清华紫荆一楼”文件夹，认为拍法不规范，会显著增加算法难度。检查时50个文件对应25张不同照片，另一半为同内容副本。用户要求结合这些资料定义可执行的标准、任务认领和两类群公告。
7. 2026年10月16日形成三份文档：采集规范与照片判例、任务认领与群运营、采集协议与算法程序改造方案；另有两份公告文本及三份PDF。当时只做文档，没有在本任务实施新算法。
8. 2026年10月17日，后续交接提交把这些Markdown及公告纳入Git；其他食堂范围扩展代码也有本地提交。这些变化不等于菜单素材自动处理已经实现。
9. 2026年10月19日，用户要求打包交给另一位AI评审，并提醒文档已在GitHub。本轮只读核对确认远端dev与本地HEAD同为5a00b868f562b4c153460a5ebd71b7dd946611cd，文档确已在该远端分支。未核验生产发布状态。

## 用户明确要的结果与约束

- 允许只有菜单，没有实物图；不能要求为了采集购买每一道菜。
- 允许一张照片多道菜、多张照片共同支持一个菜；环境照不生成菜品。
- 必要的信息必须能让数据有归属，可选信息后续由任意贡献者补充。未知如实保留，不猜填。
- 付费采集与学生自发贡献分开运营。付费任务有明确范围、认领、交付和结算；随手贡献保持低门槛。
- 菜单会变化，价格会变化，图片会补齐，错误会被纠正。需要时间、来源、版本和冲突处理，而非只增不改。
- 默认信任用户提供的事实不等于信任模型猜测。内容安全、权限、异常治理仍应保留。
- 首先讨论并验证采集规范与算法边界，再改应用代码；本次交接不授权另一个AI直接部署、迁移、发布或代用户发群公告。

## 真实材料揭示的关键困难

| 情况 | 容易犯的错误 | 应保留的事实与未知 |
| --- | --- | --- |
| 一张文字菜单含多道菜 | 把整张图当一道菜，要求人工重抄 | 按行提名称、标价及单位，保留每行来源 |
| 水果捞5、8、15元 | 自动解释成小中大，把每碗分配一个价格 | 三档价格可知，规格差异与实物对应未知 |
| 两荤一素套餐6元 | 把6元填给每个备选菜 | 组合价属于套餐；选项与单卖价格分开 |
| 自选原料价格屏 | 把0.8元推成每份或每100克；原料变成品 | 金额原文可留，计价量未明；原料单独分类 |
| 无标签多盘实物 | 按菜单顺序、外观或拍照顺序匹配 | 先归窗口；身份不明确就不精确配图 |
| 包子和蒸笼 | 凭外观猜馅料；把画面数量当每份数量 | 现场实物可见，馅料和售卖份量未知 |
| 菜单宣传图片 | 当用户实拍；无标签图分给所有菜 | 示意图与实拍分开；有明确版式关系才关联 |
| 跨页、重复与历史照片 | 重复建菜；旧图覆盖新价；缺页判停售 | 保留拍摄时间、覆盖范围与来源，更新有版本 |

这些是具体样本中的问题，不是已跑算法得到的错误率报告。完整照片索引见02号文件。

## 已提出的解决流程：仍是待验证方案

任务发布与认领 → 确认一个窗口及拍摄时间 → 采集定位照、菜单和必要规则 → 自动预检提示具体缺项 → 保存原始素材 → 异步提取菜单条目、规则和可确定的图片关系 → 少量疑点处理或整批确认 → 写入既有目录与版本链 → 后续补图、纠错及更新。

现场规范的核心是：一个窗口一组、文字可读、分段留重叠、单位和套餐小字不漏、实物标签同框或留下明确位置说明、交原图、记实际日期。建议二至四盘近拍是试行建议，不是模型已经测试出的硬上限。

首期技术目标偏向清晰文字菜单、明确图文菜单及明确售卖规则。无标签多菜实物先保存为窗口素材；不默认派给后台人员逐盘猜。清晰材料识别失败属于系统问题，不能自动要求采集员替系统录入。

原始素材、模型提取结果和正式记录应分层；最终仍复用已有菜品目录、贡献、版本和纠错机制。菜单提取与单菜营养分析分开，允许无实物图、未知单位、未知营养正常存在。

运营起步可用群公告、管理员确认和任务表，不必先开发一整套认领、积分、结算平台。两份公告不承诺未上线的自动配图或自动结算。

## 哪些是事实，哪些不是

已确认：用户诉求与上述反例；本地代表照片；三份文档与两份公告；文档已在GitHub dev；2026年10月19日抽查的批量页面仍是逐图建条目并要求菜名。

已提出但未实测：采集会话式新流程、菜单自动拆条、多对多图文关联、自动预检与放行规则、减少后期人工的效果。

尚未确认：具体模型/供应商组合、可靠阈值、真实覆盖率与错误率、处理延迟和成本、自动入库的最终政策、付费标准、实际资料接收渠道及生产上线状态。

原方案中的“后期人工下降至少70%”“无逐条人工处理比例80%以上”仅为待讨论验收目标。不能引用成现有成绩，也不能只统计成功样本。
