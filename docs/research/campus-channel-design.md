# 高校通道：社团发起的校园饮食数据共建（方案 v2，2026-11-06）

状态：方案，未写业务代码、未动线上数据。分支 `feat/campus-channel-design`（基于 `feat/research-weight-v2`，因为高校通道直接复用 v2 的称重流程）。
相关文档：[中餐称重 Benchmark 采集方案](chinese-food-weight-benchmark-plan.md)、[称重科研计划 v2](research-weight-v2-takeout-design.md)、合作提案草稿 [campus-channel-partner-proposal.md](campus-channel-partner-proposal.md)。

## 0. 一页结论

1. **高校通道是"社团 + 活动"级别的采集**：一个健身社团在一个时间窗口里发起活动，成员扫码加入，提交的数据自动带上学校、社团、活动归属。个人「称重科研计划」不变，高校通道复用它的称重流程，只多了归属和活动规则。
2. **全程由社团自己跑，我们不到现场、不接触食堂、不做人工审核**。我们只负责建活动、提供小程序和一页规程；审核、定级、发积分全部自动完成。
3. **数据按"克重从哪来"分四层，只有用秤称出来的三层是真值**：自带秤、称重日、同一道菜称多份；没秤的核心成员用精准模式拍照，那是模型估算，只用来扩充食堂菜品、看大家吃什么、给社团出报告，**永远不进 benchmark 标签**。
4. **自动读秤是这一版的关键**：成员拍秤的照片，模型读出数字自动填上，不用手打；读数对不上就当场重拍。这一步既省掉了 v2 里最麻烦的手打数字，也让自动审核有了依据。
5. **首批四校同开**：清华、北大、中国农大、上交。清华、北大已有食堂菜品库，第一周就能称重；农大、上交菜品库几乎是空的，第一周先由社团用「食堂采集」把菜单采上来。
6. **激励很轻**：活动期间只给健身协会核心成员送标准版会员（能用精准模式）；称重样本自动发积分；奖品由社团自己定，我们可以少量赞助；秤由社团自备。
7. 剩下需要你拍板的只有两三件小事，见[第 9 节](#9-待你决定)。

## 3. 合作模式与各方价值

### 3.1 各方得到什么

| 参与方 | 出什么 | 得到什么 |
|---|---|---|
| 健身社团 | 组织成员；自备秤；办称重日；2–3 人采菜单 | 社团营养报告（成员整体饮食结构、蛋白质来源、各食堂高蛋白和平价选择）；活动素材（"AI vs 我 vs 秤"挑战）；校际排行榜；共建证书、优秀团队展示、数据集致谢；我们视情况少量赞助社团自己的奖品 |
| 核心成员 | 称重或拍照记录自己在食堂吃的饭 | 活动期间标准版会员（能用精准模式）；称重积分；个人"估重眼力"成绩；数据集致谢 |
| 普通成员 | 有秤就称，没秤可以用自己已有的会员或普通模式记录 | 称重积分；个人"估重眼力"成绩；数据集致谢 |
| 我们 | 小程序、自动审核、核心成员会员、远程支持 | 中餐称重真值（benchmark）；四校食堂菜品库与份量分布；种子用户；"与 X 校健身社团共建"的品牌 |

普通成员不送会员，所以没秤又没会员的普通成员只能用普通模式记录。这部分记录照样计入活动，但在报告里和精准模式分开统计（见 4.2）。

### 3.2 首批怎么开

四校同开，规程一样，按"有没有菜品库"分两类：

- **A 类（清华、北大）**：第 1 周就能称重、拍照，记录直接挂到已有的菜上。
- **B 类（中国农大、上交）**：第 1 周由社团里 2–3 个人用「食堂采集」采 1–2 个食堂的菜单（采集员按现有规则按窗口计奖励），同时开放称重；第 2 周起精准模式记录才能挂到菜上。

我们不到现场，所以每校的启动靠三样东西：一页规程（怎么称、怎么拍、称重日怎么摆）、一段 3 分钟演示视频、和社团负责人的一次线上沟通。

### 3.3 谁出面、签什么

| 对象 | 谁出面 | 签什么 |
|---|---|---|
| 社团 | 社长或活动负责人（个人身份签） | 你的「合作确认书 V1.1」，补几条，见提案草稿第二部分 |
| 成员 | 本人 | 小程序里加入活动时勾选研究授权（v2 已有，版本号随样本保存），不另签纸面文件 |
| 食堂 | — | 暂不接触 |

社团一般不是法人，初稿"实际签约的个人 / 有权签约组织"的写法是对的。我们不给社团现金，就不涉及社团收款的问题。

## 4. 数据分层（核心）

### 4.1 四层数据

| 层 | 谁、在哪 | 克重怎么来 | 是不是真值 | 存在哪 | 用途 |
|---|---|---|---|---|---|
| **W1 自带秤** | 有秤的成员，食堂打包回去、宿舍、外卖 | 称重科研 v2 流程（多盒、吃完称、常用容器），读数自动识别 | 是 | `research_weight_samples`，渠道 `campus_self_scale` | benchmark 验证集 / 测试集；份量分布 |
| **W2 称重日** | 社团定时定点摆秤（训练场、活动室，或打完饭在食堂餐桌上自己称），成员端着自己的餐来称 | 社团的秤；托盘、碗的皮重预先存成活动共用容器 | 是（证据最齐、规程统一） | 同上，渠道 `campus_station`，带称重日场次 | benchmark 测试集主力；给精准模式标误差（4.5） |
| **W3 同菜多份** | 同一窗口同一道菜，成员轮流买来称，攒够 5–10 份 | 同上 | 是 | 同上，渠道 `campus_same_dish`，挂菜品 ID | 每道菜的份量分布；给精准模式记录当弱标签（4.3） |
| **E 拍照估算** | 没秤的成员，日常在食堂吃饭时拍照 | 模型估算：核心成员用精准模式（俯拍 + 45°），其他人用自己的模式 | **否** | 普通 `user_food_records` + `analysis_tasks`，另用关联表挂活动和菜品 | 见 4.2，**不进 benchmark 标签** |

W1–W3 都是现有称重科研 v2 流程，只多带活动归属和菜品 ID；E 层就是正常记一餐，后台在记录保存后挂一行关联。

W2 不需要食堂同意：成员买的是自己的饭，在餐桌上称自己的饭和平时吃饭没有区别。社团想更正式一点，也可以把称重日放在训练场或活动室。

### 4.2 拍照估算为什么不能当标签，能用来做什么

**不能当标签**：拿我们模型的估算当答案，再用它来考我们的模型，模型永远"答对"。哪怕换别家模型来考，测的也只是"像不像我们的模型"，不是"准不准"。用户手动改过的克重同样不是真值（人眼估重误差往往更大），只单独标成 `user_adjusted`。

**也不能拿来训练**：用自己的输出训练自己，只会把现有偏差固化下来。

**能做的事**：

1. **食堂菜品库**：哪些菜被吃得最多、哪些菜库里还没有。没有的菜进「食堂采集」的待采清单，被吃得多的菜优先做 W3。成员拍的照片可以作为菜品图候选。
2. **校园饮食结构**：三餐时间、主食和肉菜比例、食堂与外卖占比、训练日和休息日的差别。只看相对比较和趋势，并标上 4.5 测出来的误差范围。精准模式和普通模式分开统计，不混在一起算。
3. **社团营养报告**：同上口径，按社团汇总。
4. **模型稳定性**：同一道菜被多次拍照估算的离散程度，和 W3 实测的份量波动对比。这件事不需要标签。
5. **按菜找系统偏差**：某道菜的估算分布对比它的 W3 实测分布。比如模型总说宫保鸡丁 300 g，实测是 220 ± 30 g，就能发现偏差。这是用独立真值在**分布层面**做的检验，不循环；但不能据此说某一餐估得准不准。
6. **决定下一次称什么**：模型最没把握、各次估算差得最远的菜，排进下一次称重日和 W3 的清单。

### 4.3 同一道菜的份量分布当弱标签

- 同一窗口、同一道菜称 5–10 份，得到这道菜的份量分布（均值、标准差、P10–P90）。
- 拍照记录挂到这道菜上之后，"这一份大概率在 P10–P90 之间"就是它的**弱标签**。用法是按菜统计估算落在区间里的比例、整体偏高还是偏低，不当作单条样本的答案。
- 弱标签成立的前提：同一窗口、同一时期（菜单变了、过了一个学期就重新称）；称重时可以勾"加了饭 / 少要了"，这些样本不进份量分布。
- 成员买来称，反映的是学生**实际拿到**的份量，包括不同阿姨、不同时段的差异。

### 4.4 存放规则：真值和估算从结构上分开

- 每条克重都带来源 `label_source`：`scale_measured`（W1/W2/W3）、`model_estimate`（E）、`user_adjusted`（用户改过的估算）。
- **真值只存在** `research_weight_samples`。E 层只在关联表里，**不写进** `research_weight_samples`。
- 进评测集（`food_weight_labeled_samples`）只能走"审核通过 → 加入评测集"这条路，它只读 `research_weight_samples`。E 层数据在代码上没有入口能进评测集。评测集的 `metadata` 带上渠道、学校、活动、自动审核版本，方便按来源筛选。
- 导出数据集时按 `label_source` 分文件。

### 4.5 给精准模式标误差：称重日顺带称一部分

- 称重日，没秤的核心成员照常先用精准模式拍照记一餐，再端到秤上称。这一餐同时有一条精准模式记录和一条 W2 称重样本，两者自动关联（`paired_food_record_id`，按同一用户、同一场次、时间相近匹配，页面上也可以手动选"这就是我刚记的那餐"）。
- 每校攒到 50–100 对，就能给出"精准模式在这所学校食堂的实际误差"，社团营养报告里的估算数字都带上这个误差范围。
- 这些配对也是可发表的"真实场景误差"，但评测模型时仍只用称重真值和评测照片重跑，不用当时记下的估算。

## 5. 和个人称重计划的关系：社团、活动、成员

### 5.1 概念

| 概念 | 含义 | 现有可复用的 |
|---|---|---|
| 学校 / 校区 / 食堂 / 窗口 | 已有目录 | `schools`、`school_campuses`、`school_canteens` 和窗口表 |
| **社团** | 健身社团；属于一所学校 | 新表 `campus_orgs` |
| **活动** | 一个社团的一期采集，有起止时间、核心成员名额、目标 | 新表 `campus_campaigns` |
| **成员** | 扫码加入活动的用户，角色：负责人 / 核心成员 / 成员；记录有没有秤 | 新表 `campus_campaign_members` |
| **称重日** | 社团负责人在小程序里建的场次（日期、地点、餐次） | 新表 `campus_station_sessions` |
| 菜品 | 食堂菜品库 | `campus_food_catalog_items` |
| 菜单采集 | 社团里指定的人采菜单 | 「食堂采集」+ 采集员申请/授权（`campus_collector_*`），按窗口计奖励 |
| 扫码归因 | 二维码访问、注册转化统计 | `marketing_qr` 的访问、事件和漏斗统计（加入码当作 campaign_code） |
| 核心成员会员 | 活动期间赠送标准版 | 会员赠送记录（来源类型/来源键）+ `grant-paid-membership-campaign` 脚本的逻辑 |
| 积分 | 称重样本自动通过后发分 | 称重 v2 的积分规则和积分流水 |

### 5.2 角色和核心成员

- **负责人**：我们在后台建活动时指定（社长或活动负责人，按其小程序账号）。每个活动 1–2 人。负责人可以在小程序里标核心成员、建称重日、建共用容器、看社团看板。
- **核心成员**：负责人在成员列表里勾选，不超过活动设置的名额（默认 15 人，后台可按社团改）。勾上后系统自动送标准版，到活动结束时到期；取消勾选立即停止，已用的不追回。
- **成员**：扫码加入即可。

### 5.3 归属规则

- 一个用户同一时间只在**一个进行中**的活动里。
- 成员在活动期间提交称重样本，服务端自动写入 `campaign_id` 和渠道；归属在提交时确定，之后不改。活动结束后提交的样本回到个人渠道。
- 拍照记录：活动成员在活动期间保存、并选了食堂菜品的记录，服务端在保存后写一行关联。**不改 `user_food_records` 表**（热点表，别的功能也在改）。
- 个人通道的样本不受影响，渠道默认 `personal`。

### 5.4 排行榜

- **校际 / 社团榜**：按自动通过的称重样本数排，副榜按新增菜品覆盖数排。人均数作为参考显示，避免大社团通吃。
- **社团内榜**：按通过的称重样本数排，显示昵称。社团想发奖就按这个榜发，奖品由社团定，活动页可以显示社团自己写的奖励说明。
- 不按热量、体重、蛋白质排，避免鼓励多吃或少吃。

### 5.5 社团负责人看板

- 成员数、本周活跃数、每人提交 / 通过条数、离活动目标还差多少；
- 社团营养报告：成员整体饮食结构、各食堂高蛋白和平价选择，估算数字带 4.5 的误差范围；
- 导出排行榜（社团发奖用）。

第一个月先由我们远程整理一次报告发给社团，确认社团想看什么，再把报告做成自动生成。

## 6. 激励、自动审核与防作弊

### 6.1 激励

| 对象 | 内容 | 条件 |
|---|---|---|
| 核心成员 | 活动期间标准版会员（能用精准模式） | 负责人勾选，名额内自动发放 |
| 所有成员 | 称重样本积分（沿用 v2：整份 2、分项 4、多盒 2 + 每多一盒 1，封顶 6） | 自动审核通过即发 |
| 采菜单的成员 | 按窗口奖励（现有规则） | 采集员 |
| 社团 | 社团营养报告、共建证书、优秀团队展示、数据集致谢、校际排行榜 | 完成活动 |
| 社团 | 社团自己设的奖品；我们视情况少量赞助 | 线下约定 |

拍照记录**不按条发积分**，否则会刷记录。

### 6.2 自动读秤（试点前必须做好）

v2 里读数是"拍照 + 手打数字"，这一版改成：

1. 成员拍秤的显示屏 → 服务端调视觉模型读出**数字、单位**（g / kg / 斤 / oz / lb）、是否处于去皮 / 归零状态，**自动填进对应读数**。
2. 成员只核对。如果手动改了数字，且和模型读数的差超过秤的精度，就提示"读数和照片对不上，请重拍"，**不能提交**。不是事后驳回，而是当场让人重拍，这样样本一提交就是干净的。
3. 模型读不出来（反光、模糊、屏幕太暗）→ 当场提示重拍，最多重拍 3 次；仍读不出来时允许手填提交，但这条只能定为 C 级，不进对外数字。
4. 用一个便宜的视觉模型，每张秤照片一次调用；需要定 A 级的样本，再用第二个模型独立读一遍，两者一致才算。

这一步同时解决了 v2 实测里"三盒外卖要打 6 个数"的麻烦。

### 6.3 自动审核流水线（不设人工环节）

| 环节 | 检查内容 | 不通过怎么办 |
|---|---|---|
| 拍摄时 | 读秤（6.2）；评测照片是食物、**画面里看不到秤的读数**；读数照片确实是秤的显示屏 | 当场提示重拍 |
| 提交时（硬规则） | 沿用 v2：皮重 ≥ 连盒读数、单盒超 5000 g、读数照片重复使用 → 拒绝。新增：照片内容哈希跨用户查重；近似重复照片（感知哈希）；照片来源和拍摄时间（相册导入、非当天拍摄的标出） | 拒绝或降级 |
| 合理性 | 净重在该菜型的物理合理范围内（例：一碗米饭 50–800 g）；菜品已有 ≥ 5 份实测时，和这道菜的实测分布比较，超出 3 个标准差标出 | 标出、降级，不直接拒 |
| 顺序 | "吃完再称"的空盒照片要晚于评测照片（v2 已有） | 标出、降级 |
| 额度 | 每人每天计积分的称重样本上限（例：10 条），超出照收不计分 | — |
| 定级与发分 | 按下表自动定级、通过、发积分；`reviewed_by` 记为自动审核版本号 | — |

**合理性检查不能拿模型估算去筛真值。** 如果"实测和模型估算差太多就拒"，留下来的就全是模型本来就估得准的样本，benchmark 会系统性偏向模型擅长的菜，误差被低估。所以合理性只看物理范围和同菜的实测分布，**不看模型估算**。

**自动定级：**

| 等级 | 条件 | 用途 |
|---|---|---|
| A 候选 | 所有读数两个模型读数一致；皮重有照片证据（先称 / 归零 / 吃完称，不是常用容器）；评测照片来自相机；无任何标记 | 冻结测试集从这里分层抽取 |
| B | 通过硬规则，但有轻微标记，或皮重来自常用容器，或只有一个模型读数 | 验证集、公开验证集 |
| C | 读数是手填的（模型没读出来），或评测照片来自相册 | 开发集，不进对外数字 |
| 拒绝 | 硬规则不过 | 不计入 |

**质量怎么证明**（不是审核，是给论文和对外数字用）：建议每月从自动通过的样本里随机抽 50 条看一眼，算出自动审核的错误率。冻结测试集定稿前，把入选的样本过一遍。不做这一步流水线也能照常跑，只是对外说"标注准确率"时没有依据。【待决定 D9】

### 6.4 防作弊

- 社团奖励和排行榜都只按"自动通过"计。
- 负责人不能改审核结果，也看不到改审核结果的入口。
- 同一张秤照片、同一张菜照片不能被两个人用（内容哈希 + 感知哈希）。
- 核心成员名额有上限，活动结束会员自动到期。
- 某个成员的样本被抽查发现问题时，系统自动把他其余样本降为 C，直到他之后的样本重新攒够干净记录。

## 7. 小程序与后台形态

### 7.1 小程序

- **入口**：「我的 → 科研共建」现在只有「称重科研计划」，加第二项「高校共建」；称重科研计划首页如果检测到用户在进行中的活动里，顶部显示"我的社团活动"卡片。
- **活动落地页**（`packageExtra/pages/campus-campaign/index?code=…`）：**游客能看**活动介绍、学校和社团、排行榜；点"加入"才要求登录（符合微信审核要求）。二维码、链接都直接指向这里。
- **成员流程**：扫码 → 看活动 → 登录并加入（勾研究授权，选"我有秤 / 没秤"）→ 活动首页：
  - 进度：社团离目标还差多少、我的提交 / 通过；
  - 「用秤记一顿」→ 现有 v2 记录页，带活动上下文，读数自动识别，地点默认本校食堂，可以选窗口和菜品；

  - 今天的称重日（时间、地点），点进去直接用场次和共用容器；
  - 排行榜。
- **负责人页**：成员列表（勾核心成员，显示名额）、加入二维码、建称重日、建共用容器（称一次空托盘并拍照）、进度和报告、导出排行榜。

### 7.2 后台

- 社团和活动管理：建社团、建活动（时间、指定负责人、核心成员名额、目标）、生成加入码和二维码。每个社团只建一次，之后社团在小程序里自己跑。
- 称重科研页：加"学校 / 社团 / 活动 / 渠道 / 自动定级"筛选；显示每条的自动审核明细（读数、各项检查）；默认不需要操作，只用于抽查和排查问题。
- 菜品份量分布页：按菜品看所有 W3 样本，算均值、标准差和区间。
- 自动审核看板：每天提交数、自动通过率、各类拒绝原因、重拍次数、读秤失败率。
- 导出：按 `label_source` 分文件。

## 8. 落地节奏

### 8.1 阶段

| 阶段 | 时间 | 内容 |
|---|---|---|
| 准备 | 2 周 | v2 上线；读秤 + 自动审核；M1 + 活动、加入、核心成员会员、称重日、排行榜、拍照记录选菜品；一页规程 + 3 分钟演示视频；和四校社团线上沟通、签确认书 |
| 读秤实测 | 准备期最后 3 天 | 用 5–10 种常见厨房秤各拍 20 张，测读秤准确率；低于 95% 就先改提示词或换模型，再开活动 |
| 试点 | 4 周 | 四校同开。第 1 周：社团启动分享 + "AI vs 我 vs 秤"挑战 + 第一次称重日；农大、上交同时采菜单。第 2–4 周：每周 1–2 次称重日，自带秤的成员日常称；每校挑 10 道热门菜做 W3 |
| 复盘 | 第 5 周 | 看第一个月指标，决定扩校、把社团报告做成自动生成 |
| 扩校 | 第 2–3 个月 | 社团在小程序里自助申请活动（我们在后台一键通过）；优先已有菜品库的学校（苏州大学 315 道 / 8 个食堂、上海几所、厦门海洋职院等） |

### 8.2 第一个月的目标（可衡量）

| 指标 | 每校目标 | 合计（四校） |
|---|---|---|
| 加入成员 | ≥ 20 | ≥ 80 |
| 其中核心成员 | ≤ 15 | ≤ 60 |
| 活跃 ≥ 2 周的成员 | ≥ 10 | ≥ 40 |
| 自动通过的称重样本（W1+W2+W3） | ≥ 150 | ≥ 600 |
| 其中 A 候选 | ≥ 50 | ≥ 200 |
| 做了份量分布的菜（≥ 5 份） | ≥ 10 道 | ≥ 40 道 |
| 挂了菜品的拍照记录 | ≥ 300 | ≥ 1200 |
| 精准模式 + 称重配对（4.5） | ≥ 25 | ≥ 100，得出第一个"真实场景误差" |
| 农大、上交新采菜品 | ≥ 100 道 | ≥ 200 道 |
| 流程指标 | 读秤准确率 ≥ 95%；一次读出率 ≥ 85%；自动通过率 ≥ 80%；自带秤每餐耗时 ≤ 3 分钟；称重日每人 ≤ 1 分钟 | |

参照：benchmark 第一版目标是约 1000 份整份 + 300 份分项。第一个月拿到 600 条通过样本，就超过一半。

秤由社团自备，称重样本量取决于社团里有多少人有秤。建议在和社团第一次沟通时先问一句"大概有多少人有食物秤"，少于 10 人的社团，目标按比例下调，重点放在称重日。

**止损线**：第一个月合计通过的称重样本 < 200，或自动拒绝 + 重拍放弃的比例 > 30%，就先停扩校，回头改流程（多半是称重太麻烦或读秤不稳）。
