# 10–20 倍用户增长容量模型

## 模型原则

1. “用户量翻 10–20 倍”不等于所有资源线性翻 10–20 倍。计算、数据库写入和队列吞吐应按峰值请求与业务动作放大；对象存储按新增媒体量放大；缓存按活跃 key 与 TTL 放大；CDN按实际下行流量放大。
2. 当前生产业务容器 CPU 峰值较低，但整机 CPU 近 14 天达到 81.33%，且所有组件共用单节点。第一目标是消除单点和资源争抢，第二目标才是扩容。
3. 目标运行水位：稳定期 CPU 不超过 50–60%、内存不超过 65–70%；单节点或单可用区故障后仍能承载活动流量；关键资源保留至少 30% 突发余量。
4. 采购清单分为“10 倍建议起步档”和“20 倍/大促预留档”。后者可通过弹性上限、按量实例和自动扩容实现，不要求全部长期包年。

## 推荐规格推导

- 计算：当前 FoodLink + CoachLink 主环境合计峰值约 0.315 vCPU、2.58 GiB，但 worker、监控、K8s 控制面与 dev 环境占用大量共享资源。生产迁入独立 TKE 后，以跨可用区 3 节点作为高可用底座，10 倍使用 3×4C8G；20 倍使用 3×8C16G 或 4C8G 节点池自动扩至 6–9 节点。
- PostgreSQL：当前物理数据仅约 587 MiB，容量不是瓶颈。起步选择双机高可用 4C16G / 200GB；20 倍预留 8C32G / 500GB。先不购买只读实例，读负载持续超过 60% 或慢查询证明读压力后再加 1 个只读节点。
- Redis：当前仅 1.14 MiB。10 倍选择 1GB 标准高可用（主从、跨可用区）；20 倍选择 2–4GB。只有持续 QPS、热 key 或容量逼近单分片上限时才升级集群架构。
- Kafka：当前 145 MiB、lag=0、吞吐很低。优先选 CKafka Serverless 或最小多可用区高可用档，10 倍预留生产 5 MB/s、消费 10 MB/s、100–200GB；20 倍预留生产 10 MB/s、消费 20 MB/s、300–500GB。主题副本数 3、生产主题至少 6 分区，以便扩 worker。
- 网络：当前主机 14 天出站峰值约 14.4 Mbps，直接乘 20 为约 288 Mbps，但图片应由 COS + CDN 承担，不能用该数字直接购买源站公网带宽。源站 CLB 先按 50–100 Mbps 可突发档，CDN 以当前账单为基准准备 10 倍与 20 倍流量包报价。
- COS/CDN：当前云端对象量和月流量未取得。谈判时要求按“当前月均 ×10 / ×20”两档报价，并单列存储、GET/PUT 请求、CDN HTTPS 请求、下行流量、回源流量、日志投递费用。可先用 2TB 与 5TB 月 CDN 流量作为商务占位场景，但最终必须用最近 30 天账单替换。

## 扩容触发阈值

- TKE：Pod CPU 连续 5 分钟 >60% 扩容，<25% 持续 20 分钟缩容；生产 API 最少 3 副本；节点池保留 30% 可分配余量。
- PostgreSQL：CPU >60%、连接 >60%、存储 >65%、P95 查询延迟恶化或 IOPS >60% 时评估升配；存储 >75% 自动告警。
- Redis：内存 >60%、连接 >60%、P99 >2ms、淘汰数 >0 或热点阻塞时升配；启用持久化仅用于必须保留的状态，纯缓存允许重建。
- CKafka：生产/消费吞吐 >50%、磁盘 >60%、消费 lag 超过 1 分钟处理量时扩吞吐、分区或消费者。
- CDN/COS：CDN 命中率目标 >90%；回源带宽或 5xx 异常上升时检查缓存规则、鉴权与源站保护。

## 必须补测的数据

- 代表性用户旅程的 RPS、并发数、P50/P95/P99、错误率与第三方 AI 接口限流。
- PostgreSQL 峰值连接、TPS、慢查询、缓存命中率、IOPS 与 WAL 增长。
- Redis 按命令 QPS、key 数、TTL 分布、热点 key、大 key。
- Kafka 每主题生产/消费字节率、消息大小分布、保留周期。
- COS 当前容量、日新增对象、平均对象大小；CDN 最近 30 天流量、峰值带宽、HTTPS 请求数和命中率。
