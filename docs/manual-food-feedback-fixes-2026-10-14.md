日期：2026-10-14。交付范围：微信前端、Go 后端代码，提交同步到 dev 和 main。用户取消体验版上传，改由另一台电脑进行交互验收。

## 问题与处理

| 问题 | 原因 | 本次处理 |
| --- | --- | --- |
| 自定义18g浓缩咖啡添加后变350g，热量被放大 | 自定义商品返回时继续套用按名称推断的普通咖啡350ml规则；前端又将自定义单位显示为g | custom来源保留用户明确填写的默认份量和营养，跳过咖啡/蛋类名称推断；普通营养库默认规则保留 |
| 营养标示份量与添加份量容易混淆 | “实际重量”和标签营养基准同时在商品表单中出现 | 改为“默认一份重量 g”和“标签营养每多少 g”；填写标签热量后按基准换算，实际摄入仍在本餐清单修改 |
| 商品录错后没有编辑、删除入口 | 卡片整行点击只会加入本餐；服务端虽支持同名覆盖，但没有按ID修改/删除流程 | 自定义卡片增加“编辑”入口，菜单可编辑资料或删除；按商品ID、当前用户更新，允许改名，阻止同名冲突；删除采用已有status软删除 |
| 商品删除后可能从最近记录重新出现 | 最近记录从历史食物快照重建商品 | 最近列表排除已删除商品；前端同步移除列表和缓存，并防止当前请求回填已删除商品 |
| 选第一种食物后容易直接提交整餐 | 底栏一项即显示直接保存，查看清单是可选流程 | 底栏改为“选好了，核对本餐”，只打开清单；清单可改克数、移除、继续添加，最后“确认提交本餐”；允许单食物餐，保存增加重复点击锁 |
| 识别后的完整点评不能完整回看 | 结果页和记录页展示范围不同；部分回退文案只在结果页存在 | 保存结果页实际展示的营养比例/吸收文案；记录详情补比例建议和进食顺序；相同食物与摄入量时，从原识别任务恢复已有点评字段，否则依据当前记录生成营养点评 |
| 手动餐没有点评 | insight仅保存“手动记录，数据来自…”的来源说明 | 生成明确标注来源的“营养点评”，展示本餐营养与供能比例、进食顺序等；当天页面按餐次汇总，同餐次多条记录合并计算 |
| 餐食修改后点评仍可能针对旧份量 | 原修改接口只更新营养，未更新点评 | 营养更新时重新计算并保存点评，移除不再适用的旧情境建议；回看时不套用摄入量不匹配的原识别点评 |
| 商品照片数量少 | 自定义表单每次仅选一张 | 支持最多4张商品实拍照片，逐张预览、移除，保存全部图片引用；此项未扩充公共带图商品库 |

## 数据与兼容边界

- 修改商品会更新当前未提交清单的商品资料及营养，但保留该清单中已经选择的实际摄入克数。已保存的饮食记录继续使用原快照，不因商品修改或删除而重写。
- 不自动纠正历史已经以350g保存的记录。历史真实摄入量需要本人确认，再通过“修改记录”调整。
- 18g标签基准、默认一份、本次摄入量与冲调后整杯重量分别处理。本次没有引入所有液体1ml=1g的假设。
- 手动餐点评基于已记录的营养数据，不调用新AI模型、不新增积分扣费，界面标注为营养点评；原识别点评可继续展示为AI点评。
- 供能比例按蛋白质/碳水/脂肪的4/4/9系数计算，缺少营养时显示数据不足，不把缺失视为健康或均衡。
- 不新增数据库列或表，不需要迁移。进食顺序与来源标记是响应字段（gorm忽略），从原任务或当前记录恢复；营养点评使用现有insight/PFC/absorption/context字段保存。
- 原任务缺失、原文未保存或摄入已改变时，不能承诺恢复历史模型原文；此时提供当前记录的营养点评。
- 本人从当天记录进入详情使用鉴权接口，关闭公开记录也能查看自己的记录；公开分享继续遵循原隐私权限。

## 另一台电脑的运行准备

1. 拉取最新dev或main，并确认当前源码含本文件和新增的`meal_advice.go`、`meal-record-advice.ts`。不要在两分支分别安装重复依赖或生成重复大型副本。
2. 必须使用本次代码的后端。仅更新前端、仍连接旧后端时，编辑/删除接口不会生效。此轮只交付代码，没有将云端服务部署或微信上传作为完成结果。
3. 后端配置使用验收用数据库与测试账号；业务服务不在启动时迁移，本次也不需要结构迁移。Windows子进程的TEMP/TMP/TMPDIR/GOTMPDIR/FOODLINK_TEST_TMPDIR设到本机D盘独立验收目录，禁用不需要的任务worker。
4. 前端通过根目录`.env.development`的`TARO_APP_API_BASE_URL_OVERRIDE`指向实际验收后端，例如`http://127.0.0.1:3010`。不要把密钥、token或个人账号放进本材料。
5. 先通过`scripts/dev-process.ps1 -Action Status`检查已有进程，再用该管理器启动或复用backend/weapp；前端使用`npm run dev:weapp`，不要为本地迭代运行生产build。
6. 微信开发者工具打开同一`apps/wechat`项目，保留验收账号；如需自动化，使用项目weapp-devtools/miniprogram-automator，开启9420。只清理本次验收用的商品和记录，保留原账号数据及其他服务。

## 必须实际点击的验收清单

| 场景 | 操作 | 预期与证据 |
| --- | --- | --- |
| 浓缩咖啡18g | 新建验收咖啡，默认一份18g、标签每18g、34kJ；保存商品后点一次＋ | 商品及清单为18g、约8.1kcal；再次点＋为36g、约16.2kcal；不能变350g。拍摄商品列表与核对清单 |
| 普通库与自定义蛋类 | 对比普通黑咖啡、标准鸡蛋、自定义12.5g蛋类商品 | 普通库仍使用原合理默认；自定义保留12.5g，不被标准个重覆盖 |
| 编辑商品 | 点“编辑”→编辑商品资料，改名、热量、默认份量，并把某营养改为0；保存，再退出重进 | 同一商品ID被修改；0值能保存；未产生同名旧商品；已选实际重量不变、营养更新 |
| 防止错覆盖 | 用另一账号或不存在ID调用保存/删除；将名称改成另一已有商品名 | 服务端拒绝越权/不存在ID及同名冲突；失败时原商品资料保留 |
| 删除及取消 | 先取消一次删除，再确认删除；退出重进并检查自定义/搜索/最近列表 | 取消无变化；确认后不再出现；此前已保存的饮食记录仍可看；留截图 |
| 防误提交 | 加一项→点“选好了，核对本餐”→继续添加→加第二项→核对→确认提交 | 前几个步骤不保存整餐；最终仅一条完整记录；重复快速点击确认不会重复保存。另验单食物餐可提交 |
| 多张照片 | 添加2–4张实拍图，预览、删除中间一张、保存商品，重进编辑 | 图片数量/顺序保持；删除的图不重新出现；上传期间不能误保存半成品。留截图 |
| 手动整餐点评 | 保存两种食物的一餐，进入当天记录及本人详情 | 有明确“营养点评”及来源说明、供能比例、顺序；不把数据来源说明冒充AI点评 |
| 同餐次多记录 | 同一天早餐分两次记录，再看当天记录 | 早餐整餐点评合并两条记录计算；早餐和早加餐分开，不混成全天点评 |
| 完整识别点评回看 | 识别结果页截图后保存，离开，再从当天记录进入该条详情 | 可查看已有健康/比例/吸收/情境内容以及顺序、比例建议；检查实际摄入一致；字段原本为空时允许营养数据回退 |
| 修改已记录摄入 | 改某食物克数或移除食物，再回看详情 | 热量及供能比例和新数据一致；不继续显示仅针对原摄入量的点评 |
| 隐私与边界 | 关闭公开记录后从本人当天记录进入；尝试公开分享读取 | 本人详情可用；公开权限依原设置；营养全缺失显示不足，不编造点评 |

用专门命名的验收商品和记录完成操作，不拿两条不同时间/不同热量的早餐截图当作同一记录前后对比。每组保留操作前后截图、记录ID和结果，失败时注明具体按钮、页面和API状态，不记录token。
