# 所有食堂共用批量上传

2026-10-16，本地实现；尚未执行共享库迁移、提交或发布。

## 使用范围

「我的」入口和目录标题统一为「食堂」。目录的全部、校园、社区园区范围均显示一个「批量上传」按钮，不再要求先切校园。内部旧路由和 API 名称暂保留，避免破坏已有链接。

| 类型 | 申请范围 | 上传时必填地点 |
| --- | --- | --- |
| 校园 university | 学校，可细到校区/食堂 | 现有目录中的学校、校区、食堂 |
| 社区 community | 社区，可细到食堂 | 社区名称、食堂名称 |
| 园区 office_park | 园区，可细到食堂 | 园区名称、食堂名称 |
| 公司 corporate | 公司，可细到食堂 | 公司名称、食堂名称 |

非校园没有学校或校区字段。一次填写地点、楼层和窗口，连续拍照或多选，一批最多30道，每轮最多9张；每道照片和菜名必填，价格与份量可后补。已有照片时禁止直接切换食堂类型，防止误归类。

## 授权与兼容

继续复用采集员申请、Admin「食堂采集」审核及批次接口，不新增逐菜人工预审。非校园申请可只限定机构，或进一步限定食堂；后端按类型、机构、食堂与有效期检查权限，不允许凭校园授权上传其他机构，也不允许给非校园批次塞入学校目录ID。

原两张 collector 表增 venue_type、organization_name、scope_canteen_name，school_id 改为可空。旧校园记录默认为 university，原ID、范围、有效期保持；新增非校园唯一索引与范围CHECK。北京AI原点社区和AI原点社区在授权匹配中使用同一名称。

新版 profile 请求附 `include_venues=1` 取得全部类型；旧客户端不附该参数，继续只取得校园授权，避免其「第一条授权就是学校」的旧假设出错。

## 迁移与发布顺序

需先核对目标库、schema与现有约束并取得对应共享库操作授权，再从 backend 运行：

```powershell
go run ./cmd/migration -config-dir . -only-canteen-collectors
```

本轮没有连接或迁移线上数据库。确认迁移后再发布后端和小程序；只上传前端不能启用新类型。完整迁移和原校园专项迁移也调用同一扩展逻辑，HTTP启动不自动迁移。
