# 食探「一起吃」功能与 UI 提案

日期：2026-10-10。状态：设计提案，尚未确认实施、未改业务代码、未发布。用户已明确首要人群为「同学同事、同校同城找饭搭子」。下述试点范围、功能优先级和界面是建议，不能当作用户已确认的开发需求。

后续交付：用户已要求制作简易交互原型。已提供同名目录 `prototype.html`，本地 http://127.0.0.1:8767；包含圈子双页签、排行榜、发起/申请/确认/活动房间。仅授权并完成原型，不等于授权生产实现。操作说明和验证范围见同目录 README.md 与 design-qa.md。

## 产品主线

围绕一顿具体的饭建立关系：知道何时吃、在哪里吃、花多少钱、还缺几个人，然后申请加入、完成见面，饭后愿意再次一起吃。

建议从一个高校校区或办公园区起步，先满足当天、步行可达的午晚餐。首轮可招募 20–50 名自愿参与者，这是试点建议，不是已有用户规模。校园和园区复用同一套约饭对象，后续逐片区扩展同城；校园餐厅须明确校外人员能否进入，距离近不等于可进入。

产品循环：发现约饭 → 申请并获确认 → 饭前沟通 → 见面吃饭 → 自愿记录/晒餐 → 再约一次。

第一版同时包括发布/留言审核、举报拉黑、取消通知和发起人处理申请。这些直接影响约饭是否能顺利完成，应与主流程一起交付。

初期暂缓：全城陌生人地图、复杂人格问卷、AI 自动拼桌、保证金/平台代收餐费、公开信用分、完整群聊系统、组队健康排行榜。先验证有人能约成、会回来约第二顿，再扩展。

## 五个主要页面

### 1. 圈子 · 找搭子

沿用底部「首页 / 分析 / 中央拍照 / 圈子 / 我的」，中央拍照仍用于记录。圈子内部新增「找搭子 / 晒餐」，进入找搭子时选择校园/园区/附近片区；不新增底部 Tab。

首屏顺序：简短标题和消息入口 → 两个内容页签 → 地点与日期/餐次筛选 → 我的约饭待办 → 约饭列表。现有排行榜进入晒餐的次级入口；好友管理、加好友入口收进消息/关系页面。

#### 原有排行榜的位置（补充提案）

用户反馈概念「看起来不错」，并追问原有排行榜如何处理。原概念图只展示找搭子页，未展示晒餐页及排行榜入口，不代表删除已有榜单；尚未获得业务代码实施授权。

建议在「晒餐」页顶部保留一条常驻、紧凑的「本周榜单」预览，显示用户榜与食物榜两个入口，每侧最多一行真实摘要，点击直达现有完整榜单。这样进入晒餐即可发现榜单，不需要打开更多菜单；找搭子首屏继续优先展示约饭。

- 用户榜沿用「全体记录」「好友健康」及现有完整榜单页面。
- 食物榜沿用蛋白质、纤维、钙及更多营养素入口，细项放在榜单页，预览无需全部铺开。
- 原有统计口径、排序和历史记录保持既有行为；本提案只调整入口布局，不把约饭报名或见面次数计入健康榜。
- 不另加底部导航或占据首屏的大型排行榜区域。没有数据时保留榜单入口并显示空态，不编造名次。

约饭卡片的信息顺序：

1. 发起人、小范围身份说明；自填学校/园区必须标「自填」，未验证不显示认证标识。
2. 一句话邀约，例如「午休一起吃碗热乎的」。
3. 开始时间、还差几人，作为最强的信息。
4. 地点、人均预算与 AA/各自付款。
5. 可选的口味/交流偏好，如「清淡一点」「轻松聊聊」。
6. 已确认人数/总人数、「查看约饭」。未同意公开头像的成员只显示占位头像和人数。

预算、时间、剩余人数比营养数据和个人照片更突出。卡片无需食物大图，发起时也不强制传图。发起按钮固定在列表之外，滚动区预留空间，不压住最后一张卡片。

### 2. 约饭详情

首屏完整交代时间、地点、预算、人数、付款方式和通行要求。下面展示发起人自愿公开的介绍、饮食/聊天偏好，再展示报名规则。公共餐厅名称可提前展示，让人判断能否前往；桌号、集合点备注和活动讨论仅获确认成员可见。

底部随状态切换：申请加入 → 待确认（可撤回）→ 进入约饭；已满、已取消、已过期分别显示原因。删除/退出和举报使用次级操作。不能把点击申请等同于成功约饭。

### 3. 发起约饭

表单优先复用地点目录，支持手动选公共餐厅；无定位权限仍可选校园或片区。时间与地点必须确定后才能发布；「待定地点」先保留草稿，避免加入后才发现不方便。

必填：时间、地点、预算、人数、付款方式、可见范围。可见范围第一版建议「当前片区公开」或「仅邀请链接」；仅邀请链接可以转发，不等于已验证同校/同事，仍需发起人确认。学校/企业认证是独立后续能力。

可选：口味、交流偏好、补充说明。常见组合做模板，例如「工作日午餐，3 人，各自付款」，不要求填写长篇个人档案。

### 4. 约饭房间

时间地点固定在顶部，带地点导航；系统事件突出成员加入、退出、活动变更和取消。讨论内容只对获确认成员开放；退出后停止接收新消息并撤销房间访问权限。

更改时间/餐厅属于实质变更，成员状态进入待重新确认，保留原名额到确认期限；逾期才释放。第一版无需实时语音、图片群聊、转账。现有私信可继续用于双方自愿的一对一联系，但不能自动扩大陌生人消息权限。

### 5. 饭后与个人名片

饭后自愿确认到场，未点击不等于爽约；只有一方指控也不能直接公开处罚。产品先收集私下体验反馈与举报，不做公开评分排行榜。

名片以自愿公开的口味、常去片区、公开晒餐为主。私人饮食记录、体重、健康档案、补剂和营养目标不因加入饭局而自动公开。拍照记餐仍由每人确认自己的菜品和份量，不把全桌消费自动记到每个人名下。

## UI 视觉约定

- 沿用当前 Meal Orbit 色板：背景 `#f6f5ed`、表面 `#fffef9`、主色 `#21543e`、正文 `#243d31`、次要文字 `#626f65`。
- 390px 宽设计基准；正文 14–16px，常用触控区域至少 44px；先用留白和分隔组织层级，少用大阴影。
- 绿色用于主要操作，剩余人数可用低饱和暖色点缀；状态不能只靠颜色区分。
- Skeleton/spinner 表示加载，不出现「加载中」文字。空态保留当前筛选，并提供「换个时间」「发起一顿」；不自动扩大范围后冒充同校结果。
- 地理位置被拒绝时展示手动地点，不阻断浏览；距离仅在来源可靠时显示。步行分钟需要路线估算支持，只有经纬度时显示「约 X km」并注明直线距离，不能编造到达时间。
- 概念图：`meal-companions-2026-10-10/concept.png`。图中人物、地点、消息和人数均为虚构示例，并非真实活动或已上线功能。
- 概念图呈现了不同餐次卡片，以说明内容形态；其中「午餐」筛选下出现晚餐是示意不一致，实施时必须纠正为仅显示匹配餐次。标题和筛选区域也应进一步压缩，优先让第一张约饭卡完整进入首屏。

## 接入食探已有流程

首页的选餐建议、校园食堂或食物详情可新增「找人一起吃」入口，带入地点/菜品草稿。页面展示草稿并由用户确认时间、人数和预算后才发布，推荐行为本身不发起约饭。

记录后的分享仍用现有能力；若该记录源于本人参加的约饭，可自愿关联活动，形成回顾。其他成员是否被展示或被 @，需要本人同意；约饭历史不自动生成公开健康画像。

## 匹配与状态设计

第一版先用可解释规则。硬条件包括可加入状态、活动开始/截止时间、地点范围、可见性、双向拉黑、通行条件、预算约束。通过后，再按时间接近、地点便利、偏好相容、邀请关系排序。定位缺失和预算未填分别明确处理，不能虚构匹配分数或身份认证。

活动生命周期：草稿 → 开放报名 → 开始 → 结束；开放报名也可进入取消或过期。「已满」由已确认成员数决定，成员退出可重新开放；超过截止时间不再招募。

申请生命周期：待确认 → 已接受 / 已拒绝 / 已撤回 / 已过期；已接受之后可退出。待确认申请不占名额。批准操作要在服务端事务中核对人数，幂等处理重复点击，不能仅依靠前端按钮禁用防超额。

建议独立新增约饭领域，数据包括活动、参与申请、讨论/系统事件、反馈；可以复用用户、地点、通知、审核和拉黑服务。饮食记录只保留可选关联，不把饭局硬塞入私人饮食记录表。具体表结构需在实施时遵守迁移 DO 与幂等迁移规则，本轮未修改数据库。

活动时间保存明确时区；校园/园区当地时间展示，不能使用开发机时区决定餐次。到点后的推送只在用户授权且微信能力支持时发送，站内待办作为可靠入口，不承诺后台永久在线或必达。

## 试点与判断标准

建议先在一个校园或园区，集中一个固定午餐时段，邀请真实种子用户自愿发起活动。提供微信邀请卡片，每张带明确的时间、地点和余位；冷启动可优先邀请熟人，随后开放片区探索。没有活动时说明为空，不伪造报名人数或种子内容。

用这些指标决定是否扩展，不只看浏览量：

| 指标 | 建议口径 |
| --- | --- |
| 首次获确认速度 | 从发布到首个非发起人成员获接受的时长，报告中位数和分布 |
| 报名成局率 | 已开始活动中，开始时至少有 1 个非发起人获接受且未退出的占比；取消活动另报，避免幸存者偏差 |
| 确认到场率 | 成局活动中至少两位参与者分别确认到场的占比；同时报告反馈覆盖率，不将未反馈判为未到 |
| 再次参与率 | 首次确认参与后的 14 天内，再次被接受且活动开始的用户占比，仅计算观察满 14 天的用户 |
| 体验问题 | 临时取消、申请久未处理、投诉及骚扰报告，结合样本量分析 |

首轮先建立基线，不预设已经证明可行的转化率或匹配效果。连续验证能约成、再次参与和处理取消之后，再扩大同城覆盖，随后考虑固定饭搭子、候补及自动拼桌。
