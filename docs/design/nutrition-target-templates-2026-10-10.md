# 食探：多套饮食目标模板与按天选择

日期：2026-10-10。状态：产品设计提案，未实施、未发布；用户提出需求，尚未确认具体交互和实施范围。

## 需求与建议

用户希望预设多套热量及三大营养素目标，今天选择哪套就用哪套，减少碳循环、训练日和休息日频繁修改数值的成本。脂肪达到合理摄入范围后，不应仅为进度条补齐脂肪。

建议采用“基础目标 + 多个可复用模板 + 每个日期的实际目标”。普通用户继续使用基础目标；需要周期变化的用户开启模板选择。模板可以叫训练日、休息日、高碳日、中碳日、低碳日或自定义名称，不把所有人限定为一种碳循环。

第一版完成手动切换、模板管理、当天临时微调、历史留存和下游目标同步。周计划自动安排作为第二阶段，不根据记录到的运动自动改变目标。

## 现有能力与接入点

## 用户使用流程

1. 从当前基础目标创建第一个模板，复制后修改即可创建训练日、休息日等方案。
2. 首页保留现有营养面板右上角「目标」入口，用它打开方案选择；面板内显示当前方案名称。入口跟随选中日期，查看昨日时编辑10月9日方案。
3. 点击入口打开底部选择面板，每套模板展示名称、热量和蛋白质/碳水/脂肪摘要，当前选择有明确标记。
4. 点击一套模板就立即应用到当前日期，关闭面板并更新目标、剩余额度和后续选餐建议；底部短提示提供“撤销”。面板标题与说明明确当前日期，不再增加一个重复的确认按钮。
5. 面板内提供“今天临时调整”和“管理模板”。前者只改这一天；后者编辑未来可复用的模板，两个动作不共用含糊的“保存”按钮。

模板管理支持新建、复制、重命名、编辑、设为默认、删除。删除默认模板前明确选定新的默认方案；历史仍保留原名称和数值。默认方案可以是基础目标，不强迫用户创建训练日模板。

未来未安排的日期使用默认方案，不静默沿用昨天的训练日。模板数量与名称可扩展，不把“三个模板”做成数据结构限制。

## 模板数值与编辑规则

每套模板包含热量参考目标、蛋白质/碳水/脂肪参考克数，以及三种营养素的合理区间或评价方式。主界面先展示易理解的克数，区间和锁定设置放在编辑页的进阶选项。

| 项目 | 建议的产品行为 |
| --- | --- |
| 热量 | 围绕计划目标评估，不追求绝对等于某个数字；微小误差不提醒补吃 |
| 蛋白质 | 强调达到合理需要，达到后显示充足；超过适宜范围不持续奖励 |
| 碳水 | 主要用于训练负荷与能量分配的变化，可随模板调整 |
| 脂肪 | 使用适宜区间；区间内显示适宜，低于下限提示关注，高于上限提示偏高 |

默认创建训练/休息模板时建议蛋白质相近，主要调整碳水及必要的总热量；允许用户自定义休息日更高蛋白，但不把它当成默认科学规则。脂肪区间的来源和适用条件需要沿用个人健康目标规则，不硬编码同一个克数给所有人。

编辑提供两种清楚的方式：

- 自由设置：直接输入各宏量克数，展示对应热量参考。
- 优先调整碳水：锁定蛋白质和脂肪参考克数，调整热量时主要调整碳水；使用近似公式 `碳水克数 = (热量 - 4 × 蛋白质克数 - 9 × 脂肪克数) / 4`。若计算为负或超出适用范围，解释冲突并要求调整设置，不输出负数或静默改动锁定值。

4/4/9用于计划参考数值的一致性检查，不用于改写食物识别结果或历史摄入，也不要求实际食物统计毫无误差地符合该式。旧目标原值保留；启用新编辑方式时才让用户选择如何处理不一致。

微量营养、纤维等健康目标默认共享，避免创建每套模板都填一遍；共享规则更新适用于未来日期，已保存日期仍保留实际采用的目标版本。第一版不增加完整的微量营养周期设置界面。

## 进度和推荐必须一起变化

单纯改变进度条分母不够。首页、餐次预算、选餐建议、聊天中的当日饮食决策、分析页以及周汇总必须消费同一份日期目标及评价方式。

例如脂肪已经在适宜区间、蛋白质也充足、热量与碳水仍有空间时，可以优先推荐合适的主食或水果，而不是因为脂肪还没达到参考点就建议加油或坚果。热量也已足够时，不为填满某条营养进度而建议继续吃。

脂肪偏低或偏高仍需要在评价中体现；蛋白质不是越多越好，碳水也不能无限补。选餐仍遵守整体营养质量、忌口和既有健康规则，不能只优化三大营养素的进度。

模板热量若已考虑训练安排，不再把运动记录的热量自动叠加一次。运动记录用于展示和后续建议，不能静默覆盖用户选定模板。

聊天中用户提出的临时假设须标成“本次咨询目标”；要改变当天计划时，由明确的应用动作进入同一按日目标链路。

## 日期和历史规则

- 同日可以切换。实际已吃的内容与数量保持原样，只改变该日目标及之后的建议；如果新目标已被当前摄入超过，真实显示偏高，不修改摄入凑达标。
- 修改模板默认只影响未来应用，不追溯修改已经保存的日期；若要应用到今天，使用单独明确的动作。
- 每天保存实际使用的模板名称、模板版本、目标数值、评价区间、来源和修改时间，历史图表读取该日期的快照。
- 历史日期的目标修改是明确的日期操作，不能因查看页面或编辑模板自动发生；保留修改记录和来源。
- 没有真实历史目标的旧日期不能伪造。实施时按原有已知数据尽量保留；无法还原的日期标记为历史参考目标，不宣称恢复了当时真实计划。
- 周总热量达成情况比较“本周实际总摄入”和“逐日目标相加”，训练日与休息日各用自己的目标；蛋白质和脂肪也保留逐日区间达标情况，避免周平均掩盖每日问题。
- 沿用现有业务日期和时区口径，不在新增功能里混用服务器 UTC 与用户界面日期。

目标解析优先级建议为：日期临时调整 > 日期手动选择模板 > 周计划（后续） > 默认方案 > 基础目标。手动选择某一天只覆盖该天，不自动改整个周期。

## 数据与实施边界

建议分别维护可复用模板和每日目标快照：模板有用户归属、名称、版本、目标值、区间及归档状态；每日快照按用户和日期唯一，保存实际采用值及来源，不能只存模板 ID 再从当前模板读历史。

未显式应用的日期通过有生效日期的默认/基础目标版本解析，读接口不因查询自动创建业务记录。历史参考与新功能正式快照应可区分。

不要把整套模板状态只塞进前端缓存，也不要继续用一个长期 `dashboard_targets` 字段覆盖每天的不同选择。现有每日目标表是否扩展，应按迁移 DO、旧数据兼容及唯一约束审查确定，避免建立重复的日期目标系统。

实施须遵守项目数据库流程：先在迁移 DO/幂等迁移代码落结构，再核实目标库运行迁移命令；非本地库先取得明确确认。所有按日读写验证用户归属，并采用事务保持模板应用和快照一致。

新增缓存按用户和日期隔离，切换方案后刷新该日推荐/分析，模板编辑清理相关列表缓存，并接入“我的→清除缓存”。离线应用只能明确显示为待同步；后端未确认前不能声称云端推荐已经采用新目标。

## 第一版验收重点

1. 创建、复制、切换不同目标模板后，该日首页和推荐/分析目标一致。
2. 今天临时调整不改变模板，不影响明天；未选择的日期使用默认方案。
3. 当天已有摄入再切换，摄入不变，剩余额度正确，超额真实显示。
4. 模板改名、编辑或删除后，历史目标不变化；历史日期操作不会误改今天。
5. 脂肪在合理区间内不提示强行补齐；偏低、偏高仍有合适的评价。蛋白质超量不持续加分。

7. 相关页面与交互实施后，使用 weapp-devtools 尝试真实运行时导航、选择和截图验证；定向测试使用 D 盘任务目录，不跑开发全量构建。

## 营养依据和产品推论

- [ISSN：蛋白质与运动立场声明（2017）](https://pubmed.ncbi.nlm.nih.gov/28642676/) 强调每日充足蛋白质及运动后的恢复需求，运动促进合成的效应可持续至少24小时。“训练/休息默认保持相近蛋白、主要调整碳水”是据此给出的产品默认建议，不能把“休息日必须更高蛋白”当成文献结论。
- [Horton 等：脂肪与碳水过量进食试验（1995）](https://pubmed.ncbi.nlm.nih.gov/7598063/) 在特定的短期过量进食条件下观察到脂肪过量摄入具有更高的能量储存效率。不能把该条件下的结果直接等同于日常“吃脂肪就长脂肪”。
- [Schwarz 等：碳水摄入变化与燃料利用（1995）](https://pubmed.ncbi.nlm.nih.gov/8675642/) 观察到碳水过量摄入会提高碳水氧化、降低脂肪氧化；即使直接由碳水合成脂肪有限，也可能影响脂肪储存。因此不能把代谢解释成“碳水必须按固定顺序用完糖原和活动，最后才可能增加体脂”。

这些依据支持保留能量平衡与合理宏量摄入的整体评价，不构成碳循环一定比均衡每日目标更有效的证明。本提案不提供用户个人摄入处方；具体数值需结合个人档案、训练安排和目标。

## UI 与交互细化：2026-10-10 用户追问

用户表示前一版抽象说明仍不清楚，希望具体看到 UI、交互和功能细节。本轮交付对话内可点击示意 `nutrition-target-ui-demo.html`；这不是正式小程序改动，不调用后端、不写用户真实数据。示例模板数值只用于展示操作效果。

### 首页

沿用现有一体营养面板：左侧热量圆环、右侧三大营养素、底部「营养概览」展开条。现有右上角「目标」作为方案选择入口，面板内显示当前方案名称与能量；不另加一条常驻“切换”按钮。“只调整今天”和“管理所有方案”放在选择面板中。顶部日期切换后，所有入口跟随该日期；未来日期展示计划目标。

脂肪用区间条和当前摄入标记，旁边显示“适宜/偏低/偏高”。区间内即使没有到达参考克数也显示适宜，不用百分比暗示必须补满。

### 选择方案面板

底部面板标题为“今天用哪套方案？”，副文案“仅用于10月10日，点击后立即切换”。每项显示名称、默认标记、热量及三大克数摘要；当前方案显示“正在使用”。点击其他方案直接应用并返回首页，可撤销。整个日常流程是打开面板、点一项，共两次点击。

面板底部提供“只调整今天”和“管理所有方案”，不在选择列表中同时展开四个数字输入框。

### 管理模板

列表每项有名称、目标摘要、默认标记和“编辑目标 / 用于今天 / 更多”。“更多”进入复制、设默认和删除；底部主操作为“新建一套方案”。编辑当前已经用过的模板后，列表提示“当天保留旧目标”；需要更新今天时，再明确点击“用于今天”。

第二个入口位于“我的 → 饮食方案”，用于集中管理。由“我的”进入管理后返回“我的”；由首页选择面板进入管理后返回首页。页面使用用户更容易理解的“方案”称呼，模板是可复用目标的数据概念。

正式首次启用时，先从用户当前目标保存“常规日”，按需复制创建训练日和休息日，不强迫首次填写三套数字。示意为了便于评审，预置了三套样例。

### 新建与编辑

字段按模板名称、热量、调整方式、蛋白质/脂肪、碳水排列。调整方式开关为“调整热量时只改变碳水”，辅助文案为“蛋白质和脂肪保持你设定的克数”。开启后碳水由剩余能量计算；关闭后直接编辑三大，由三大反算热量，避免四个输入相互冲突。

脂肪适宜范围折叠显示，展开后设置上下限。保存主按钮为“保存方案”，上方说明“保存方案后供下次选择；已安排的日期保持原样”。新建支持自定义名称，复制预填原值。

### 只调整当天

复用数字编辑表单，隐藏模板名称编辑，显示“基于训练日”；顶部说明“仅改变10月10日，原模板和其他日期保持原样”，按钮为“保存今天的调整”。保存后首页名称显示“训练日 · 临时”，可撤销；不自动新增模板，也不更新训练日模板原值。

### 默认、删除和历史

默认模板只决定未单独安排的日期，不覆盖已经安排的日期。删除当前默认模板前，提示先设其他默认。删除曾用模板后，该日和历史仍读取保存快照。示意可以切到昨天和明天查看这些区别；所有日期和行为仍为展示数据。

### 验证边界

示意可用 DOM 交互检查验证选择、撤销、编辑和快照数据行为。没有改动微信页面/组件、启动 watch 或切换开发者工具账号/API；未将这份示意接到小程序运行时，也不能据此宣称真实 API 链路或像素布局验收通过。正式实现后仍需项目要求的 weapp-devtools 验证。

### 目标的范围和继承

- 宏量：热量、蛋白质、碳水、脂肪参考值与适宜区间。
- 维生素和矿物质：默认继承个人健康档案参考值；可在方案中独立覆盖，不跟着训练/休息日热量同比缩放。
- 其他营养指标：纤维用参考值；钠和饱和脂肪用限制值；总糖与胆固醇仅记录。纤维、总糖、饱和脂肪、胆固醇不统称为维生素/矿物质。
- 原型共 21 项，覆盖当前项目目标配置：6 种矿物质、11 项维生素相关指标、4 项其他营养指标。数值取自 `apps/wechat/src/pages/index/utils/nutritionTargets.ts` 的现有默认配置，代表示例档案，未逐项校准成新的 DRI 标准或个人处方。
- 正式创建应根据年龄、性别、生理阶段等档案选择适用的参考值；引用标准须保存版本、参考类型及单位。RNI/AI、饮食控制值和 UL 不能混成一条“必须补满”线。特殊人群已有指导应优先，不能给全部人统一提高钾/铁/维生素剂量。

模板只保存继承方式和改动值；应用到某一天时保存完整有效微量目标快照。模板编辑/删除、档案后续更新，都不能追溯改写已保存日期。当天临时微量调整仍只影响当天；碳循环的一组训练/休息方案默认继承相同微量目标。

### UI 和交互

热量、三大营养素、微量营养必须共用现有营养面板。微量部分默认折叠，点击面板底部「营养概览 · 展开更多」在原位展开 21 项四列网格；点击「收起」折叠，不跳转详情页面，也不在热量卡之后新增独立摘要区。展开区提供目标管理。分析示例使用同一面板与同一天目标。此项为用户明确纠正，覆盖此前独立微量区与详情页提案。

营养记录缺失显示“数据不足”，不填 0 或显示确定缺乏。低于参考使用“记录未达参考”，达到使用“记录达到参考”，不奖励无限提高摄入。钠使用“已记录值未超限/超出限制”，不鼓励补到上限；由于数据可能不完整，不把记录值直接当完整实际摄入。未来日期只展示计划目标，不评估摄入。

方案编辑表单增加折叠区“微量营养与其他指标”。默认只读并说明“继承档案”；勾选“为这套方案单独设置”后允许改相应单位的参考/限制值。关闭后恢复档案值。保存模板不覆盖今天；明确应用才保存新的当日宏量和微量快照。临时编辑同样支持微量调整和撤销。输入最大值仅用于本原型数值校验，不代表推荐值或 UL。

### 常用预设库

入口为“我的 → 饮食方案 → 从预设创建”，也可由首页「目标 → 管理所有方案」进入。五个起点如下：

| 预设 | 创建行为 | 饮食或营养侧重 |
| --- | --- | --- |
| 均衡日常 | 创建一套，可改名和数字 | 以现有基础目标起步，多样食物、纤维和微量充足 |
| 高蛋白 | 创建一套，可改名和数字 | 示范增加蛋白质后由剩余能量计算碳水；正式克数按个人情况生成 |
| 碳循环 · 训练与休息 | 一次创建两套；详情可改两天热量 | 蛋白质/脂肪相同，主要改变碳水，不自动排周计划 |
| 地中海风格 | 创建一套，保留可修改目标及食物侧重 | 蔬果、全谷、豆类、鱼、坚果和橄榄油 |
| DASH 风格 | 创建一套，保留可修改目标及食物侧重 | 少盐、多蔬果、全谷、低脂乳制品；关注钾、钙、镁、纤维 |

单套预设先查看详情，再进入编辑，保存后回自己的方案列表。碳循环显示两套目标和自动碳水计算后一次添加；不足两个位置或数值不可能时整组拒绝，不出现半组。创建/导入不会自动改变今天，仍需选择或“用于今天”。每套导入后的目标可编辑、复制、设默认或删除。

地中海和 DASH 是食物选择与饮食结构，不用唯一一组宏量比例代表，也不宣称只设几个数字就已遵循完整饮食模式。原型展示其食物侧重和优先关注指标，微量数值继续继承个人档案。减脂/维持/增重应由个人能量目标决定，不另用一套统一的“减脂热量”覆盖所有预设。

### 依据与验证

- [WHO 健康饮食（2026）](https://www.who.int/news-room/fact-sheets/detail/healthy-diet) 强调充足、平衡、适度与多样性，区分游离糖限制和其他糖数据。产品不把已有总糖字段直接套上游离糖上限。
- [AHA 地中海饮食](https://www.heart.org/en/healthy-living/healthy-eating/eat-smart/nutrition-basics/mediterranean-diet) 说明并非一种唯一标准饮食，描述主要食物结构；本原型食物侧重据此设计。
- [NHLBI DASH](https://www.nhlbi.nih.gov/health/dash-eating-plan) 描述均衡食物结构、较低钠和富含钾/钙/镁/纤维的食物；产品继承个人档案目标，没有把官方 2000 kcal 餐单的一组数字强塞给全部用户。
- 碳循环组与高蛋白的数字仅为可修改示例，不宣称碳循环优于其他模式，也不是所有人通用的摄入建议。

定向 DOM 交互检查通过：21 项完整展示、缺失数据/限制语义、档案继承/独立/恢复、调热量不改微量、当日快照/撤销、五种预设、碳循环热量联动和整组容量检查、导入不应用今天、风格信息保留、旧版本状态升级、状态体积及导出源一致。原有入口/返回、CRUD/default/history 等流程也回归通过。未新增项目测试、构建或服务，不触碰微信账号/API；没有将 DOM 检查当作浏览器像素、真实微信或真实营养数据链路验证。
