## 已实现

- 圈子「找搭子 / 晒餐」。找搭子支持学校/园区/餐厅关键词、餐次、今天、附近3公里和预算筛选、分页、发布及我的约饭；顶部消息入口可查看站内系统通知。晒餐保留原互动、用户榜和食物榜，榜单采用紧凑预览，完整榜单及原统计口径保持不变。
- 专用 `packageMeal` 分包：详情、发起、我的约饭、房间。发起人批准/婉拒申请，开始前可移出已加入成员；申请者撤回或退出；发起人取消；活动和留言可举报。被拉黑或失去房间权限后仍提供活动举报、我的约饭和清理参与状态的入口。
- 2–4人含发起人，待确认不占位。活动行锁防止最后名额重复批准；申请 revision 防止旧页面审批新的申请。申请、发布、留言与通知采用请求键/唯一约束控制重复写入。通知与状态变更在同一数据库事务内保存。
- 公开活动只返回活动信息、公开昵称和头像；申请集合及管理 revision 只向发起人开放，成员名单只向当前成员和发起人提供。私人饮食和健康数据未加入约饭 DTO。
- 房间只向发起人和当前已接受成员开放；退出/移出即撤权。取消/结束后停止新留言，向仍具成员资格的人保留历史。页面可见时每10秒刷新，隐藏或离开停止，不新增后台 worker。
- 内容审核失败关闭发布、申请和留言；拉黑检查覆盖发起人及已加入成员。举报保存目标快照，管理员可隐藏活动/留言或驳回举报。隐藏活动通知发起人、申请者和已加入成员。
- 原生微信地点选择与附近定位统一 GCJ-02；手写地址不伪造坐标、不参与附近筛选。首版时间输入为北京时间，未来30天、默认90分钟。付款仅为 AA/各自付款约定。
- 401 接入重新登录，业务403保留原含义；过期响应不能清除另一个已登录账号。登录回跳保留 `packageMeal` 完整路径，系统消息按 UUID 解析约饭跳转。

## 接口与迁移

业务接口根为 `/api/meal-meetups`，标准响应 `{code,message,data}`：

| 方法与路径 | 用途 |
| --- | --- |
| GET /、GET /:id | 公开列表、详情；有登录态时返回本人参与状态 |
| POST /、GET /mine | 发起、我的约饭；需要登录 |
| POST /:id/applications | 申请，包含 request_id 和可选 note |
| POST /:id/applications/:user_id/respond | 发起人 accept/reject/remove，包含 revision |
| POST /:id/leave、POST /:id/cancel | 撤回/退出、取消；退出包含 revision |
| GET/POST /:id/messages | 当前成员房间；发消息包含 request_id/content |
| POST /:id/reports | 举报，reason 及可选 event_id |

新增 `meal_meetups`、`meal_meetup_participants`、`meal_meetup_events`、`meal_meetup_reports` 四类迁移 DO；唯一约束、检查、外键及索引落在 DO/幂等迁移中。服务启动不自动迁移。

管理员沿用现有 adminAuth：GET `/api/admin/meal-meetup-reports` 读取前50条待处理举报，POST `/api/admin/meal-meetup-reports/:report_id/resolve` 提交 `{action:"hide"}` 或 `{action:"dismiss"}`。本轮提供处理 API，未新增 Admin 可视化面板。
