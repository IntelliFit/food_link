# 饮食社交「一起吃」实施计划

日期：2026-10-10。状态：用户已明确「OK，开始执行吧」，首版核心代码已实现，完整微信运行验收因自动化超时未完成；实施结果见 `implementation-report.md`。用户已查看 localhost 原型并反馈「基本没问题」，原型的页面结构作为本轮基线。生产目标数据库迁移与发布另按实际目标执行授权，当前不执行。

原型：`prototype.html`，http://127.0.0.1:8767。产品规则说明：上级目录 `meal-companions-2026-10-10.md`。

## 第一版交付目标

让一个校园或办公园区的人能完成：找约饭 → 申请加入 → 发起人确认 → 房间沟通 → 吃饭 → 自愿记餐/再约。圈子采用「找搭子 / 晒餐」，晒餐顶部保留紧凑的用户榜与食物榜入口。

第一版包含：约饭列表/筛选、详情、发布、我的约饭、申请处理、成员讨论、退出/取消、站内通知，以及必要的内容审核、举报和拉黑处理。付款约定仅展示 AA/各自付款，不处理资金。讨论先做文本留言与系统事件，不引入完整即时群聊。

首页推荐入口、邀请分享卡片和饭后记餐作为主流程完成后的衔接。第一版先上线片区公开活动；「仅邀请链接」在完成邀请令牌、访问权限和微信分享验收后再开放，不能将原型中的选项直接视为生产能力。

## 编码前采用的默认规则

这些是减少首版歧义的实现建议，用户后续可调整。

| 项目 | 默认规则 |
| --- | --- |
| 人数 | 总人数含发起人，默认 3 人，支持 2–4 人；发起人发布即占 1 个名额 |
| 申请 | 需发起人确认；待确认不占名额；同一用户同一活动只有一个当前申请状态 |
| 接受 | 事务内重新验证活动有效、人数、双向拉黑和申请状态；重复操作返回已有结果 |
| 退出 | 申请可撤回；已加入可退出，释放名额并写系统事件；发起人取消整个活动 |
| 时间 | 发布必须是未来时间；到开始时间停止申请和批准；结束时间采用可解释的默认时长并在详情显示 |
| 修改 | 首版发布后不修改时间/地点/人数，避免已确认成员基于旧安排赴约；提供取消并重新发起 |
| 地点 | 公共餐厅/食堂，支持现有地点搜索；地点缺少可靠坐标时不参与距离筛选，也不编造距离；校园通行要求显式展示 |
| 片区 | 以所选地点与地点数据为基础，不凭自填学校认证身份；定位拒绝时可手动选地点 |
| 房间 | 仅发起人和已接受成员可读写；退出/被移除后撤销访问；取消后只向原成员保留通知/必要历史，讨论停止 |
| 数据公开 | 约饭不自动公开私人饮食、体重、补剂、健康档案；晒餐沿用现有本人选择 |
| 榜单 | 复用既有接口与统计口径；只调整入口，不把约饭次数算入健康排名 |

时间保存带时区信息，餐次按活动所在地时间判断。活动查询和动作都检查时间边界，不依赖页面倒计时或新后台 worker 保证过期。

## 复用与新增范围

已只读核对 `backend/internal/app/app.go`、community/message/friend 服务及迁移模型。项目已有相关包测试，第一版不另建完整测试框架。

| 能力 | 已有实现 | 接入方式 |
| --- | --- | --- |
| 晒餐与互动 | `/api/community/public-feed`、`feed`、`feed-targets/...` | 保留既有业务与互动逻辑，调整圈子展示结构 |
| 用户/食物榜 | `checkin-leaderboard`、`health-leaderboard`、`food-nutrient-leaderboard` | 直接复用；不照搬原型虚构数值和口径 |
| 地点搜索 | `/api/location/search`、`/api/location/reverse`，校园目录能力 | 复用选地点和坐标来源；首轮明确目录缺坐标/不可进入的处理 |
| 拉黑 | `FriendService.IsBlockedEither` 等 | 列表、申请、批准、成员讨论都校验，不只前端隐藏 |
| 系统消息 | `MessageService.SendSystemMessageWithAction` | 发送加入、接受、退出、取消等站内通知，扩展前端可识别的约饭跳转动作 |
| 审核与举报 | 现有内容安全服务、内容 guard、圈子举报流程 | 复用底层能力；约饭是新增资源类型，需补目标解析及管理处置，不能直接传不存在的 feed target |
| 约饭活动与成员 | 当前检查范围未发现对应完整领域 | 新增独立模块，避免复用私人饮食记录或好友申请表承载饭局 |
| 房间讨论 | 现有 message 表面向一对一 sender/receiver | 复用界面组件、审核能力；独立存储活动文本/系统事件，校验成员权限 |

## 按顺序完成三个阶段

### 阶段一：后端规则与接口

建议新增 `backend/internal/mealmeetup/`，沿用 domain → repo → service → handler 分层，接入 `internal/app/app.go`，不建立平行的用户、消息或地点系统。

1. 定义活动、参与关系和活动事件/留言三类数据。活动保存发起人、时间、地点快照/可选目录引用、可靠坐标、预算、付款方式、人数上限、状态和可见范围。关系保存申请/接受/拒绝/撤回/退出状态，建立活动+用户唯一约束。事件保存文本留言及成员/取消等系统事件，通知投递状态可随事件记录，失败可重试且不重复通知。
2. 先落迁移 DO，再落业务模型；唯一约束、检查约束和查询索引通过 DO/幂等迁移表达。新表和外键保持可重复运行，迁移不修改既有饮食或榜单数据。
3. 实现活动查询、发布、详情、我的约饭、申请/撤回、发起人批准/拒绝、退出/取消、成员讨论。活动详情 DTO 明确划分公开信息与成员集合细节，公开列表不返回私人字段。
4. 完成鉴权、活动所有权、成员权限、人数事务、幂等、双向拉黑、审核、举报与通知。记录中文结构化日志，只记录必要用户/活动ID、状态和数量。
5. 本地临时数据库完成定向验证。真实目标库迁移时先核对配置；非本地库在明确指定目标后单独执行迁移命令，再启动/部署应用。

接口草案统一归 `/api/meal-meetups`：列表/创建、`mine`、活动详情/取消、申请及申请处理、退出、房间留言、举报。最终路由与 DTO 在此阶段确定，前端按真实契约接入，避免为每个页面重复建立同义接口。

完成标准：通过真实接口完成一场发布、申请、确认和沟通；并发抢最后一个名额不会超员；第三人不能读取房间；重复请求不重复占位；退出和取消后权限/人数正确；审核拒绝内容不公开。

### 阶段二：小程序页面与联调

1. 拆分现有较大的 `pages/community/index.tsx`：圈子页负责双页签；原动态展示与请求逻辑保留；提取紧凑榜单入口和约饭列表组件。
2. 新增详情、发起、我的约饭、管理申请和房间页面，放入合适分包；同步 `app.config.ts`、`utils/api.ts` 与类型。检查 packageExtra 容量后决定是否需要专用约饭分包，不用新页面把主包撑大。
3. 用服务端返回状态渲染待确认/已加入/满员/取消/过期；申请成功不直接跳入房间。发布或申请动作返回后的列表同步按当前账号、筛选和请求世代处理，避免旧响应覆盖新状态。
4. 页面加载用 skeleton/spinner；地点拒绝、空列表和接口错误有明确操作。扩展现有「清除缓存」覆盖新增用户感知缓存。
5. 站内系统消息支持约饭跳转，详情失效时能显示合理状态。房间采用页面可见时的短轮询/刷新，离开页面停止，不新增永久后台进程。

完成标准：微信开发者工具中的主流程可真实点击走完；晒餐和两个榜单仍可用；截图能证明圈子首屏、申请状态、发起表单及活动房间。HTML 原型继续作为视觉参考，不直接转成小程序运行代码。

### 阶段三：完整验收与试点准备

1. 使用隔离测试用户和临时数据验证：正常加入、发起人同意/婉拒、最后名额竞争、重复点击、成员退出、活动取消、时间到期、拉黑与越权访问、通知跳转、审核/举报处置。保留用户真实账号和当前服务配置。
2. 完成与改动相关的 TypeScript、ESLint、Go 包检查及代码审查；测试针对状态/权限/事务，不运行无关全量测试或完整微信生产构建。小程序运行验收遵守 weapp-devtools，复用登记的 watch/后端并在结束释放本任务登记。
3. 主流程合格后，衔接推荐地点发起、微信邀请卡片、饭后记餐与再约，逐项增加并验收。记录后的分享依赖当前独立分享改动的最终状态，不直接混入其未发布内容。
4. 收集最小试点指标：发布→首次接受时长、成局率、退出/取消、再次参与。主动发送微信邀请由用户/试点成员操作，不能因实施任务自动向真实联系人发消息。
5. 发布时按实际 dev/main、数据库目标、小程序上传范围分别核对版本；后端迁移、镜像发布、小程序上传分开记录。部署及非本地库操作按用户的发布范围执行，不把原型认可当作正式发布指令。

完成标准：约饭闭环与既有记录/榜单回归通过，审核/举报有处理入口，已知限制和试点范围写清；再选择一个校园或园区启动试点。

## 验证与磁盘约定

常规必要定向验证使用 `D:/cache/agent-tests/meal-meetup-implementation-<日期>`，测试子进程设置 TEMP/TMP/TMPDIR；Go 另设 GOTMPDIR/FOODLINK_TEST_TMPDIR。复用依赖和缓存，不安装新群聊基础设施、不创建重复大型副本。临时 PostgreSQL 在结束停止并清理，仅清本任务产物。

阶段一最需要验证人数竞争和权限边界，阶段二最需要真实小程序交互，阶段三验证完整联动。通过后不为流程重复制造产物。迁移和发布的目标确认属于实际执行时的环境确认，不能为了写计划现在要求用户批准未知目标。
